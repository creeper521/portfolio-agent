Comparison 回答该用什么组件呈现？三个方向横向对比

当前 Comparison 没有专用组件——只有一个「对比项目」按钮触发后端 COMPARE_SUBJECTS， 比较回答落回扁平 section 渲染。路线图 CONTEXT-03 要求「明确比较对象、证据配对和缺失项表达」。 下面是三个可能的设计方向，用于判断阶段 5 的 Comparison Plan Spec 该往哪走。 现在不预留契约，仅探索视觉可能性。

1 并排分栏卡片 2 项目对比 · 直观

每个项目一栏，按固定维度（背景、职责、方案、验证、状态）纵向排列。 优点：视觉对称、易扫读；缺点：维度超过 3 个项目时横向溢出，且难以做「同一维度跨项目的证据配对」。 最适合 2 项目深度对比。

方案维度对比 · 事件驱动 vs 静态分析

方案范式 运行时事件流 vs 编译期静态解析
订单履约中台

采用运行时事件驱动——订单状态机发布领域事件到 Kafka， 下游服务异步消费。核心挑战是最终一致性与死信兜底。

SQL 慢查询审计

采用编译期静态分析——解析 SQL AST，匹配规则引擎里的反模式。 不依赖运行时数据，核心挑战是规则覆盖度与误报控制。

验证方式 压测与故障演练 vs 规则覆盖率统计
订单履约中台

通过压测验证性能边界（P99 < 200ms），用混沌工程做故障注入验证补偿链路。

SQL 慢查询审计

用历史 SQL 样本集统计规则命中率与误报率（< 5%），验证规则有效性。
