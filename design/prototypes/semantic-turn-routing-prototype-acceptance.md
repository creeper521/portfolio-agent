# Semantic Turn Routing 原型验收说明

> 对应原型：`design/prototypes/semantic-turn-routing-prototype.html`
> 对应 Brief：`docs/superpowers/prototypes/2026-08-10-semantic-turn-routing-prototype-brief.md` 第 9 节
> 日期：2026-08-10 · 状态：交互验证材料，非生产代码

## 怎么用

浏览器打开 `semantic-turn-routing-prototype.html`，底部 `demo-rail` 在 A–H 八个状态间切换。每个状态展示一条用户提问 + 对应 Agent 消息。点击状态 B 的「任务摘要」条可折叠/展开；状态 C 点「按此计划继续」会跳到状态 F 模拟执行结果。

## 设计方向

方向一 · 编号线性清单 + 折叠密度（已与用户确认）。

- 任务 = 序号 `01-05` + serif 任务名 + 一行 mono 依赖标注（`↳ 需要 01、02 先完成`），不画节点图、不画连接线。
- 密度三档：状态 A 计划 UI 不出现；状态 B 折叠成一条摘要条；状态 C 完整展开 + 三选一确认。
- 与现有 `.reco-card` 序号语法同源，单一 accent、米色窗口、契约测试全部不破。

## Brief 第 9 节逐项验收

| # | Brief 验收标准 | 对应状态 | 怎么验证 | 结论 |
|---|---|---|---|---|
| 1 | 用户能在 10 秒内理解复杂计划 | C | 桌面端打开状态 C：序号 01-05 线性排列，约束条置顶（后端·面试展示·推荐 1 个），依赖用 mono 小字标注，无需翻页即可看全 | ✅ |
| 2 | 用户能区分确认和澄清 | C vs D/E | C 是「待确认」实底红标签 + 三选一按钮；D/E 是「待澄清」红边标签 + 候选选项 chip，视觉语法明确区分（确认=计划已成型等放行，澄清=缺信息无法生成） | ✅ |
| 3 | 用户能看出哪个任务失败以及为何阻塞下游 | F | 任务状态矩阵：02 标「证据不足」、03/04 标「被阻塞」并附 `reason` 一行说明阻塞原因（依赖 02 → 02 未完成 → 阻塞）；正文只渲染 01、05 两项成功的，失败任务无伪正文 | ✅ |
| 4 | 单任务体验没有被计划 UI 打扰 | A | 状态 A 完全不渲染任何计划卡/摘要条/步骤列表，只有结构化回答 + 证据 + 建议问题 | ✅ |
| 5 | 多任务摘要不取代正常回答正文 | B | 三个任务的正文完整渲染（三个 `.answer-block`），任务摘要是一条折叠在底部的摘要条，点开才显示任务清单，不遮挡正文 | ✅ |
| 6 | 不展示内部推理、工具或安全细节 | 全部 | 无 Prompt、无检索评分、无任务 ID 暴露给用户（demo-rail 是评审控件非产品 UI）、无异常堆栈、无安全规则文案（H 只用克制表达「这个请求我无法回答」） | ✅ |
| 7 | 作品集事实和通用知识来源不会混淆 | F | 每个正文块带 `.source-tag`：作品集事实（红边框）vs 通用知识（灰边框）；scope 标签也区分「作品集」/「通用知识」 | ✅ |
| 8 | 移动端可以完成确认、调整、取消和澄清 | C/D/E 移动端 | 390px 视口下：计划按钮 `flex:1` 等宽堆叠可点击、澄清 chip 全宽可点选、无横向溢出（scrollWidth=clientWidth=390 已测） | ✅ |
| 9 | 能据此决定任务上限、确认阈值和状态摘要密度 | C/F | 复杂计划 5 步触发确认、3 步自动执行（B）、单步无 UI（A）——三个阈值在同一原型里可对比，足以反推后端 `SemanticTurnPlan` 的确认阈值参数 | ✅ |

## Brief 第 4 节状态覆盖

| 状态 | Brief 要求 | 原型实现 |
|---|---|---|
| A 简单单任务 | 不展示多余计划卡 | ✅ 无计划 UI |
| B 多任务自动执行 | 紧凑可折叠摘要、顺序固定 | ✅ 折叠摘要条，展开后 01→02→03 固定序号 |
| C 复杂计划确认 | 显示任务/约束/依赖 + 三选一 | ✅ 约束条 + 5 步清单 + 依赖标注 + 继续/调整/取消 |
| D 局部澄清 | 部分可继续，只澄清受影响任务 | ✅ SQL 审计已继续，仅比较任务待选第二个主体，`clarify__continue` 标明不受影响 |
| E 关键澄清 | 先澄清主体，展示被阻塞下游 | ✅ 不执行比较/推荐，`clarify__blocked-downstream` 列出阻塞的下游任务 |

| G 计划失效 | 明确重新生成，不静默替换 | ✅ 红边框 callout + 重新生成/取消，明说不沿用旧计划 |
| H 安全边界 | 整轮终止，不显示部分计划 | ✅ 克制表达，无部分计划、无内部规则 |

## 技术验证

- **控制台错误**：0（Playwright `pageerror` + console error 双监听）
- **横向溢出**：桌面 1440px + 移动 390px，`scrollWidth === clientWidth`，无溢出
- **交互**：状态 B 折叠/展开（`data-open` false→true）、状态 C 确认跳转 F 均通过
- **响应式断点**：1279.98px（shell 圆角 12px）、959.98px（shell 全屏无圆角）、620px（单列、按钮等宽、字号下调）
- **reduced motion**：`@media (prefers-reduced-motion: reduce)` 禁用所有 transition/animation
- **键盘/焦点**：`:focus-visible` 红色 outline + offset；所有交互元素是 `<button>`，原生可达

## 视觉契约遵守

- 单一 accent `#7a2e2a`（牛血红），未引入 green/teal/cyan/purple（契约禁）
- 状态区分用「形态 + 文字」（菱形 bullet、边框、标签），不靠红绿黄
- 字体三栈：serif（正文/标题）、sans（用户消息/控件）、mono（元数据/序号/状态/约束）
- 暖黑舞台 `#1e1b17` + 米色 shell `#f3eadb` + thread `#f5e8d1`，与 tokens.css 一致

## 待定项（需后端契约反馈）

原型用 Mock 字段命名，最终契约待修订：

1. **任务上限/确认阈值**：原型用 3（自动）/ 5（确认）演示，实际阈值需后端 `SemanticTurnPlan` 定义——是否按任务数、成本、冲突、扩范围综合判定？
2. **状态摘要密度**：原型折叠态只显示「N 步·已完成 + 流程箭头」，是否够？要不要在折叠态就显示部分成功标志（如「2/3 完成」）？
3. **来源区分粒度**：`.source-tag` 区分作品集事实/通用知识，是否需要更细（如 SYNTHESIS 来源单独标记）？
4. **计划失效触发**：原型演示了失效后的 UI，但「版本/令牌过期」的具体判定（contentVersion、integrityToken、expiresAt）需后端定义。
