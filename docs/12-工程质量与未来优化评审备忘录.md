# 工程质量与未来优化评审备忘录

## 1. 文档性质

本文保存阶段性的代码与工程评审观察，便于后续复核、讨论和筛选可能的优化方向。

本文不是需求规格、实施计划、版本路线图或交付承诺。文中条目：

- 不自动进入开发范围；
- 不代表已经排期，也不指定负责人和截止时间；
- 不覆盖 `AGENTS.md`、当前代码约束、发布契约和已经确认的设计；
- 只有在单独确认实施后，才应进入 `docs/superpowers/specs/` 形成设计；
- 只有在实现和验证完成后，才应更新 `08-当前实现状态.md` 和 `11-项目演进日志.md`。

如果本文与权威需求、代码、测试结果或发布制品冲突，应以可复现证据和
`00-文档状态索引.md` 规定的权威顺序为准，并重新复核本文，而不是直接按本文改代码。

## 3. 条目语义

### 3.1 影响等级

- **高**：可能破坏公开契约、失败关闭边界、发布门禁或主要用户路径；
- **中**：可能增加维护、并发、性能、安全加固或交付风险，但当前未证明会直接造成严重故障；
- **低**：局部一致性、长期演进或在特定规模下才会显现的问题。

影响等级不等于实施优先级。是否实施还需要结合产品目标、使用规模、部署方式和成本判断。

### 3.2 证据状态

- **已复现**：通过检查、测试、接口或明确调用路径重复观察到；
- **静态推断**：依据代码结构可以成立，但仍需要运行时或压力场景验证；
- **待环境验证**：依赖真实 Provider、数据库、代理、容器或生产环境。

### 3.3 建议性质

- **修正候选**：现状与已声明契约或门禁不一致；
- **加固候选**：现状可工作，但存在可验证的可靠性、安全性或维护性风险；
- **可选演进**：只有触发条件出现后才值得设计，不应提前建设。

### 3.4 当前状态

- **开放观察**：保留问题与证据，尚未决定实施；
- **已转规格**：已经单独确认并进入设计文档；
- **已关闭**：已经修复并重新验证，或事实变化后不再成立；
- **不采纳**：经讨论决定接受现状或通过部署边界解决，并记录理由。

## 6. 并发、性能与扩展性

### C-01 超时取消不保证底层资源随准入许可一起释放

- **影响等级**：中
- **证据状态**：静态推断
- **建议性质**：加固候选
- **当前状态**：开放观察
- **判断依据**：请求超时后执行 `future.cancel(true)` 并返回，从而释放外层 admission；如果 Provider、ONNX 或其他底层调用忽略线程中断，worker 仍可能继续占用资源。
- **可能影响**：连续超时可能积累后台任务，使真实并发突破配置上限；虚拟线程数量不等于外部资源无限。
- **可能方向**：在实际资源消费区持有许可，直到 worker 真正结束；记录 late completion、cancel ignored 和真实 in-flight；增加一个故意忽略中断的压力测试，再决定是否需要有界队列、结构化并发或资源级 semaphore。
- **相关文档**：`03-可能技术选型.md`、`06-公开内容发布运行手册.md`。

### C-02 限流和幂等是单实例边界

- **影响等级**：低
- **证据状态**：静态推断
- **建议性质**：可选演进
- **当前状态**：开放观察
- **判断依据**：当前来源限流、并发状态和幂等记录位于进程内存中。
- **可能影响**：多实例部署时每个实例拥有独立计数和幂等状态，集群总体限制会放大。
- **可能方向**：单实例继续保持当前简单实现；只有明确进入多实例并出现跨实例一致性需求时，再评估网关限流、Redis 或数据库协调。
- **相关文档**：`03-可能技术选型.md`、`06-公开内容发布运行手册.md`、`10-本地PostgreSQL与pgvector运行手册.md`。

### C-03 当前测试不能证明真实模型和数据库容量

- **影响等级**：中
- **证据状态**：待环境验证
- **建议性质**：加固候选
- **当前状态**：开放观察

## 9. 可选演进方向及触发条件

下列方向不是当前待办。只有出现明确触发条件时才值得进入设计：

| 方向 | 建议触发条件 | 当前结论 |
|---|---|---|
| 集群级限流和幂等 | 明确采用多实例，且需要跨实例一致限制或请求去重 | 保持单实例实现 |
| PostgreSQL/pgvector 成为公开主存储 | Bundle 启动、发布或查询成本成为实际瓶颈，且数据库发布/回滚已独立验收 | Bundle 继续是默认安全基线 |
| 真实外部 Provider 常态启用 | 数据策略审批、密钥治理、成本、超时和降级证据齐备 | 默认关闭 |
| 更通用的 Tool Registry、Hook 或 Orchestrator | 至少有两个真实实现出现重复扩展代码，并形成稳定契约 | 不提前抽象 |
| 持久会话或私有 Copilot 产品化 | 用户价值、保留策略、认证、权限和隐私责任均已明确 | 继续使用页面内存会话与 Codex 私有工作流 |
| 集中式可观测平台 | 单机日志无法支持故障定位或发布验收，且数据最小化策略已批准 | 保持封闭诊断和结构化日志 |

## 10. 从观察进入实施的转换规则

某项观察只有满足以下条件，才可以从本文转入正式设计：

1. 已确认它仍然存在于当前代码或环境；
2. 已明确用户影响、失败模式或触发条件；
3. 已决定属于实现问题、测试问题、文档问题还是部署责任；
4. 已比较保持现状与至少一种修改方案的成本；
5. 已确定不会破坏公开安全和隐私边界；
6. 已在 `docs/superpowers/specs/` 中形成单独设计并获得确认。

完成实施后，不直接删除本文历史条目，而是将状态改为“已关闭”，补充验证证据，并在
`11-项目演进日志.md` 中记录已经发生的变化。若决定接受现状，则标记为“不采纳”并记录理由。
