# 周末登录奖励 ABTest 作品集项目设计

**日期：** 2026-08-04  
**状态：** 已确认，待实施  
**目标：** 将周末登录奖励 ABTest 作为独立一级 Project 纳入公开实习作品集，并用三个 Case 呈现实验设计、服务端实现及验证风控闭环。

## 1. 背景与目标

现有作品集已经包含“活动系统工程实践”主线，但该主线以多项活动配置和故障排查为主，无法准确承载一次重要 ABTest 活动从需求到验证的完整闭环。

本次新增内容必须做到：

- 把 ABTest 作为独立 Project，而不是协调任务或普通活动 Case；
- 准确表达本人完整、深度参与，贡献类型使用现有 `PRIMARY`；
- 同时呈现实验方法、Java 服务端能力、配置 SQL、测试、埋点、分析和回滚；
- 让页面浏览和 Agent 检索都能针对关键技术点继续追问；
- 不公开公司内部标识、原始代码、SQL、环境路径或不可验证的业务指标。

## 2. 信息架构

采用“1 个独立 Project + 3 个关联 Case”的结构。

### 2.1 Project

- slug：`weekend-login-abtest`
- 标题：`周末登录奖励 ABTest 完整闭环`
- 状态：`DELIVERED`
- 贡献类型：`PRIMARY`
- 展示层级：`PRIMARY`
- 时间范围：2026 年 7—8 月
- 技术标签：Java、MySQL、缓存、配置管理、A/B Testing、数据埋点

Project 负责说明业务问题、完整职责、总体方案、关键决策、验证方式与工程产出。

### 2.2 Case 1：实验设计与稳定分流

聚焦内容：

- 将业务需求翻译为实验假设和唯一变量；
- 明确实验单位、基线窗口、实验窗口和结果窗口；
- 按实验前历史登录天数分层；
- 在层内进行等比例稳定分桶；
- 持久化实验标签，防止跨请求、跨实例组别漂移；
- 区分分配、激活、曝光和转化。

### 2.3 Case 2：服务端能力与配置 SQL

聚焦内容：

- 新增可配置日期范围的登录天数分层条件；
- 打通规则解析、配置加载、缓存初始化、条件判断、数据查询、标签生成和活动激活链路；
- 编写活动激活规则、分层规则和版本更新 SQL；
- 使用独立实验身份隔离不同期次的历史样本；
- 处理不同地区的实验与单一奖励策略；
- 记录两期活动的配置演进、字段修正和无用代码清理。

### 2.4 Case 3：验证、观测与风险控制

聚焦内容：

- 设计分层边界、区间覆盖、层内比例、重复调用、持久化、地区隔离和版本刷新测试；
- 核对活动实例、规则数量、实验身份、缓存加载和服务实例收敛；
- 区分服务端分配与客户端真实曝光；
- 建立分配、激活、曝光、领取和结果指标的分析口径；
- 设计正常结束、紧急停止和回滚流程；
- 将已分配对象、已曝光对象、奖励状态和异常数据纳入处置。

三个 Case 均使用 `PRIMARY / DELIVERED`。

## 3. Project 公开叙事

### 3.1 摘要

深度参与重要运营活动从实验需求拆解到发布验证的完整闭环，围绕历史活跃度分层与层内稳定分桶，完成服务端实验能力扩展、配置 SQL、测试验证、埋点核对及回滚方案设计。

### 3.2 核心职责

- 将业务需求转化为可执行实验模型，明确实验假设、A/B 唯一变量、实验单位和三个时间窗口；
- 设计“历史登录天数分层、层内等比例分桶”的分流方案，并持久化实验标签；
- 扩展服务端 ABTest 条件能力，打通配置、缓存、条件和活动激活链路；
- 编写和迭代多地区活动 SQL，处理活动实例、实验身份、分层区间和配置版本；
- 设计测试矩阵，核对埋点和分析口径，并准备停止实验与回滚预案。

### 3.3 关键决策

- 先按历史登录天数分层，再在每层内部稳定分桶，以降低历史活跃度差异的干扰；
- 每期实验使用独立实验身份，避免旧标签污染新样本；
- 将“已经分配”和“真实曝光”分开统计；
- 在实验开始前冻结基线窗口，避免活动行为反向改变分层；
- 回滚覆盖配置、缓存、活动状态、持久化标签和实验数据，不以 SQL 执行成功作为完成标准。

### 3.4 工程产出

形成可复用的按日期范围统计登录天数、分层并稳定分桶的服务端能力，完成两期周末登录活动的代码与配置演进，使活动分流从一次性配置提升为具备稳定归组、可验证、可观测和可回滚能力的实验闭环。

## 4. 公开证据与事实边界

新增四条 Claim：Project 完整闭环总产出，以及三个 Case 各自的产出。每条 Claim 关联一组脱敏 Evidence。Evidence 只公开材料类型、时间范围、审核摘要和验证状态，不公开原始正文。

事实依据包括 2026 年 7 月的服务端条件能力、日期范围配置和配置 SQL 代码演进，2026 年 7 月末第二期活动 SQL，以及已整理的实验模型、服务端执行链、SQL、测试矩阵、发布验证、分析和回滚材料。

公开内容不得包含公司、产品或仓库内部标识；内部任务号、活动序列、实验 Key、数据库表名和字段原文；包名、类名、提交哈希、地区目录、服务器或环境路径；SQL 与代码原文；未公开或无法验证的业务指标；也不得将学习推演表述为已在线上执行的事实。

## 5. 页面与 Agent 行为

- Project 进入一级项目目录，并按 `PRIMARY` 展示；
- 三个 Case 进入 Case 目录并关联到该 Project；
- Project 详情页展示背景、职责、方案、关键决策、验证、结果和关联 Case；
- 新增一条 2026 年 7—8 月 TimelineEvent；
- 新增三个推荐问题，覆盖分层分桶、稳定归组以及验证回滚；
- Agent 能检索 Project 与三个 Case，并在回答中附带对应的已批准证据；
- 未知或超出公开材料的问题继续 fail-closed，不从私有知识库补全答案。

## 6. 公开数据与发布

实施时升级 `contentVersion`，新增 Project、Case、Claim、Evidence、关联关系、时间线和推荐问题，更新规范化作品集与展示数据，并重新生成检索文档、索引、Manifest 与 checksums。

运行时仍只读取 `backend/src/main/resources/public-data/` 下的已审核快照。私有 Obsidian 知识库和业务仓库仅用于人工提炼与核验，不成为运行时数据源，也不进入公开发布包。

同时更新作品集资产状态和项目演进日志。

## 7. 验证策略

### 7.1 数据契约

- Project、三个 Case、四条 Claim 和四组 Evidence 均可被 schema 解析；
- Project—Case、Claim—Evidence、Timeline 和推荐问题引用完整；
- 公开 Evidence 全部为 `APPROVED`，原始内容保持私有；
- 新旧公开项目均保持可加载。

### 7.2 页面

- 项目目录出现 ABTest 一级项目；
- Project 详情完整展示主叙事和三个关联 Case；
- Case 目录能够按项目筛选三个 Case；
- 各详情页的状态和贡献标签正确；
- 窄屏与宽屏均无布局回归。

### 7.3 Agent 与检索

- 三个推荐问题能够命中新 Project；
- 分层分桶、持久化、SQL 演进、曝光和回滚问题能够命中正确 Claim；
- 回答不出现内部标识或未经批准的原始材料；
- 无公开依据的业务效果问题返回边界说明，不编造指标。

### 7.4 工程门禁

- 后端测试；
- 前端测试与构建；
- 检索 Bundle 校验；
- 隐私检查；
- 发布包完整性检查。

- 不新增运行时私有知识库读取能力；

- 不重构与作品集内容发布无关的页面和后端模块。
