## 0. 文档定位

本文档记录"真正多任务 Agent"前端交互原型阶段**的设计决策与理由**，并标注每个决策在后续 Spec 与实现中的最终落地情况。它是 Spec 的上游交互基线，不是后端契约，也不是生产实现规范。

> **权威性说明**：本原型是 Spec 的**输入**，不是最终权威。当本文档与 `docs/superpowers/specs/2026-08-10-semantic-turn-routing-design.md` 冲突时，以 Spec 为准。Spec 在若干点上有意识地细化或修订了原型方案，本文档在这些点用「实现演进」标注说明差异与最终决策，避免读者误把原型早期方案当作权威。

原型的产出物是一份可点击验证的 HTML 演示，曾用于：

1. 修订 `SemanticTurnPlan`、确认协议、澄清协议、任务结果摘要等后端语义契约；
2. 确认任务上限、确认阈值、状态摘要密度等产品参数；
3. 编写阶段二正式 Spec 与实施 Plan。

以上三步现已完成，Spec 已确认、前端实现已落地并通过本地门禁。原型 HTML 本身仍用本地 Mock 数据、不接真实后端，仅作交互演示与历史参照。

## 1. 设计目标

### 1.1 验证四个核心问题

| # | 问题 | 原型对应状态 |
|---|---|---|
| Q1 | 复杂计划怎样展示，用户能否快速理解并确认 | C |
| Q2 | 主体或依赖不明确时，怎样一次只澄清一个决策主题 | D、E |
| Q3 | 多任务部分成功时，正文和任务状态怎样同时保持清晰 | F |
| Q4 | 简单任务、多任务自动执行和复杂计划确认怎样用一致但不过度打扰的交互 | A、B、C 对比 |

### 1.2 不验证什么

- 全站视觉改版（保持现有暖黑舞台 / 米色窗口 / Evidence Desk）；
- 后端检索、调度、模型能力；
- 持久化、跨标签页、登录鉴权；
- 开发者 DAG 编辑器（任务图要转译为用户可理解的目标与顺序）。

### 1.3 成功标准（来自 Brief 第 9 节，详见 acceptance.md）

10 秒理解复杂计划 · 区分确认与澄清 · 看出失败与阻塞 · 单任务不被打扰 · 摘要不取代正文 · 不泄露内部细节 · 来源可区分 · 移动端可完成全部操作。

## 2. 设计方向决策

### 2.1 三个候选方向

原型开工前，对"计划确认与任务状态呈现"给出了三个差异化方向让用户选择：

**方向一 · 编号线性清单**
任务用序号 `01-05` + serif 任务名 + mono 约束条 + 一行 mono 依赖标注呈现。不画连接线、不画节点。约束复用现有 `.reco__satisfied` 底盘。

**方向二 · 阶段分组卡片**
任务按"可并行阶段"自动归组，阶段卡之间用发丝线 + 箭头串联。依赖关系最直观，但视觉更重。

**方向三 · 折叠摘要条 + 渐进展开**
默认一条 mono 紧凑条，点开看完整清单。只有"待确认"状态强制展开。默认最克制。

### 2.2 选定方向一，并吸收方向三的折叠机制

**最终选择：方向一（编号线性清单）作为主方向，吸收方向三的"折叠密度"作为状态 B 的默认态。**

理由（按重要性排序）：

1. **同源 = 风险最低**。方向一本质是把现有 `.reco-card` 的 `01/02` 序号语法放大成一个任务序列。单一 accent、米色窗口、视觉契约测试全部不破。Brief 第 8 节明确把 `作品推荐-V1保守` 列为正式参考，同源方向落地阻力最小。

2. **谱线弹性好**。方向一的一个组件能覆盖三种密度：
   - 状态 A：计划 UI 完全不出现；
   - 状态 B：折叠成一条摘要条（借方向三的精华）；
   - 状态 C：自然展开成完整清单。
   这正好对应"简单任务不展示多余 UI、多任务自动执行要紧凑、复杂计划要完整呈现"的需求梯度。

3. **本次复杂计划是线性链**。Brief 给的五步计划（介绍 A → 介绍 B → 比较 → 推荐 → 总结）是线性依赖链，方向一的"编号 + 一行依赖标注"恰好够用。方向二的阶段分块是杀鸡用牛刀，对三任务场景更过度。

4. **移动端零成本**。线性清单在窄屏只是变得更窄，不需要把"阶段连接线"降级处理。方向二的箭头连线在 <620px 单列时会语义降级。

**落选方向的价值（留作后续探索）**：
- 方向二的阶段分块在**真·网状依赖**（一个任务被多个上游共同阻塞、或存在可并行分支）时直观性更强，如果阶段二正式 Spec 发现任务图复杂度超出线性链，可重新评估。
- 方向三的"默认折叠"机制已经被吸收进方向一的状态 B，不是完全落选。

## 3. 视觉语法系统

### 3.1 设计契约（不可议）

以下规则直接复刻 `tokens.css` / `AgentWorkspace.vue` / `ConversationThread.vue`，保证原型与生产工作台视觉同源、不破契约测试（`visualContract.test.ts`）：

| 维度 | 规则 | 来源 |
|---|---|---|
| 暖黑舞台 | `#1e1b17` | `--agent-stage` |
| 米色窗口（三层） | shell `#f3eadb` / thread `#f5e8d1` / evidence `#f8f3ea` | `--agent-shell/rail/thread/evidence-paper` |
| 单一 accent | 牛血红 `#7a2e2a`，辅助 `--red-hi #b65d53`、`--red-on-ink #d27d74` | `--red` |
| 禁用色 | green / teal / cyan / purple 全族（契约锁定） | `visualContract.test.ts:60-62` |
| 字体三栈 | serif（正文/标题）/ sans（用户消息/控件文案）/ mono（元数据/序号/状态/约束） | `--serif/sans/mono` |
| 圆角 | sm 8px / md 12px / shell 20px | `--agent-radius-*` |
| 动效 | `cubic-bezier(0.22,0.8,0.22,1)`，fast 160ms / state 220ms | `--ease`、`--agent-motion-*` |

### 3.2 状态表达哲学：形态 + 文字，不靠颜色

**关键决策：任务状态（成功 / 证据不足 / 被阻塞 / 待确认）一律用形态和文字区分，不用红绿黄。**

原因：
1. 契约禁用 green/teal，无法用"绿=成功"；
2. 颜色编码对色弱用户不友好；
3. 文字（"已完成" / "证据不足" / "被阻塞"）比颜色更精确——"证据不足"和"被阻塞"是两种不同的失败，颜色无法区分这个粒度。

具体语汇：
- **已完成**：mono 小字 `已完成`，无背景无边框（最低强调，因为成功是默认期待）；
- **证据不足 / 被阻塞**：mono 小字 + 红边框 + 极淡红底（`rgba(122,46,42,0.05)`），承载需要用户注意的负面状态；
- **待确认**：实底红标签 `待确认`（最高强调，需要用户行动）；
- **待澄清**：红边框标签 `待澄清`（需行动，但语义是"缺信息"而非"等放行"，与待确认区分）。

### 3.3 统一组件清单

原型抽象出五个可复用组件，构成一致的视觉语法：

#### 3.3.1 Plan Confirmation · 计划确认卡（状态 C）

```
┌ 计划 · 5 步 · 从了解到推荐 ─── 待你确认 ┐
│ 约束  后端 · 面试展示 · 推荐 1 个        │
│ 01  介绍 SQL 审计项目                    │
│ 02  介绍 ABTest 项目                     │
│ 03  比较两个项目   ↳ 需要 01、02 先完成  │
│ 04  推荐一个项目   ↳ 需要 03 先完成      │
│ 05  总结策略       ↳ 使用 04 的结果      │
│ [按此计划继续]  调整计划  取消           │
└──────────────────────────────────────────┘
```

- **约束条**：置顶（约束是决策前提，应先于任务清单看到），上下发丝线包裹成独立信息带。
- **任务行**：mono 序号 `01-05`（红色，`min-width` 对齐）+ serif 任务名 + 来源标签 + 可选 mono 依赖标注（`↳ 需要 XX 先完成`）。
- **依赖标注规则**：依赖类型枚举不外泄（见 §5 原则5），后端只返回预格式化的 `dependencySummary` 字符串，前端原样展示为 `↳ …` 一行。**不画连接线、不画节点图**。
- **三选一操作**：主按钮（实底红）`按此计划继续` + 幽灵按钮（描边）`调整计划` / `取消`。主次清晰，移动端等宽堆叠。

> **实现演进**（`PlanConfirmation.vue`）：
> - **eyebrow 概括句**：实现采用 `N 步 · {summaryLabel}`，其中概括句由后端确定性提供（`plan.summaryLabel`），缺失时回落为「N 项任务」——不前端拼接，避免瞎猜。
> - **状态机扩展**：原型只考虑「待确认」一态。实现补充了 `adjusting`（用户点过调整计划、仍在编辑，显示「调整中 · 仍可确认原计划」徽章）与 `readonly`（计划被后续轮次取代，仅作记录、不可操作）两态。
> - **来源标签**：每个任务行带 `[data-source-label]`，`PORTFOLIO` 用红边、其余灰边（见 §3.3.6）。

#### 3.3.2 Compact Task Summary · 折叠摘要条（状态 B 默认）

```
默认（折叠）:
┌ 任务摘要 · 介绍→比较→推荐 · 3 步已完成 · ▾ ┐
└──────────────────────────────────────────────┘

展开后:
┌ 任务摘要 · ... · ▴ ┐
│ 01 介绍 SQL 审计       已完成 │
│ 02 介绍 ABTest          已完成 │
│ 03 比较两个项目        已完成 │
└───────────────────────────────┘
```

- **默认折叠**：多任务自动执行时，正文是主角，摘要收起成一条 mono 条。
- **点击展开**：`aria-expanded` 切换，展开后是完整任务清单 + 状态（由 `TaskStatusSummary` 渲染）。
- **折叠态密度按结果分流**（实现最终方案，Spec §15.3 细化）：
  - **全成功** → 流程箭头 `介绍 → 比较 → 推荐 · 3 步已完成`（可读性优先）。
  - **部分成功** → 计数 + 异常摘要 `2/5 完成 · 1 证据不足 · 2 阻塞`（让用户不展开就感知到失败项）。
  - eyebrow 随状态切换：全成功显示「任务摘要」、部分成功显示「任务状态」。
- **展开触发**：部分成功时首屏自动展开（让失败项立即可见）；全成功时默认折叠。

> **实现演进**（`CompactTaskSummary.vue`）：原型初稿折叠态统一用流程箭头，并在 §9 列为「是否在折叠态显示失败计数」待定项。Spec §15.3 明确要求「用户折叠后仍显示 2/5 完成 · 1 证据不足 · 2 阻塞」，实现据此定为「全成功用箭头 / 部分成功用计数」的折中。toggle 字符用 `+/−`（mono 字体下清晰），非 chevron 旋转——功能等价。

#### 3.3.3 Clarification · 澄清卡（状态 D、E）

两种变体：

**局部澄清（D）** —— 部分任务可继续：
```
┌ 需补充信息 · 比较任务需要第二个项目 ┃
│ ◆ 你想把 SQL 审计和哪个项目比较？   │
│ [01 ABTest   选择 →]               │
│ [02 数据校验 选择 →]               │
│ [03 配置中心 选择 →]               │
│ ─────────────────────────────────  │
│ 已继续 · 介绍 SQL 审计不受影响     │
└────────────────────────────────────┘
```

**关键澄清（E）** —— 整条依赖链阻塞：
```
┌ 需补充信息 · 请指定要比较的两个项目 ┃
│ ◆ 你想比较哪两个项目？              │
│ [A SQL 审计  第一个]                │
│ [B ABTest    第一个]                │
│ ─────────────────────────────────  │
│ 被阻塞的下游任务                    │
│ ↳ 比较两个项目 — 等待主体确认       │
│ ↳ 推荐一个项目 — 依赖比较结果       │
└─────────────────────────────────────┘
```

- **红菱形 bullet**（7px rotate45）前置问题文案，复用现有 `.reco__unsatisfied` / `.problem-callout` 语汇。
- **候选选项**（`.clarify-chip`）：mono 序号 + sans 选项名 + mono hint，hover 变红边。选项来自当前公开主体目录。
- **`已继续` 条**（D 独有）：明确标出哪些任务不受澄清影响，已经执行。
- **`被阻塞的下游任务`**（E 独有）：列出被上游歧义阻塞的任务链，让用户理解"为什么不一次问完就开干"。

> **实现演进**（`TurnClarification.vue` + `ClarificationField.vue`）：
> - **输入模式扩展**：原型只有单选 chip。实现按后端 `field.inputMode` 支持 `SINGLE_CHOICE`（点选即提交）/ `MULTI_CHOICE`（多选 + 「确认选择」，带 `aria-pressed` 选中态）/ `SHORT_TEXT`（文本框 + 提交）三种。多选提交是临时兼容路径，待后端多值通道确认后切换。
> - **已继续提示点名**：局部澄清优先用后端 `continuingGoalLabels` 点名已继续任务（「已继续：介绍 SQL 审计、不受影响」），缺失才回落数量文案。
> - **下游原因白名单**：关键澄清的下游目标附原因短句，同样走 `taskReasonLabels` 白名单映射（`等待你确认比较对象` 等），不接收后端自由文本。
> - **空选项兜底**：无可选项时引导用户去输入框补充说明，不呈现死路。
> - **状态机扩展**：补充 `pending`（已提交、正在重新规划）与 `readonly`（被后续轮次取代）两态。

#### 3.3.4 Task Status Summary · 部分成功状态矩阵（状态 F）

```
┌ 任务状态 · 部分完成 · 2 项成功 ─── 展开看详情 ┐
│ 01 介绍 SQL 审计                      已完成  │
│ 02 介绍 ABTest                        证据不足 │
│    └ 公开证据不足，无法生成可信介绍           │
│ 03 比较两个项目                       被阻塞  │
│    └ 依赖 02 的介绍结果，02 未完成所以阻塞    │
│ 04 推荐一个项目                       被阻塞  │
│    └ 依赖 03 的比较结果，03 被阻塞所以阻塞    │
│ 05 后端面试通用技巧                   已完成  │
└───────────────────────────────────────────────┘
```

- **网格**：序号 / 任务名（含 reason 小字）/ 来源标签 / 状态标签，形态标记（实心圆=完成、菱形=阻塞/失败）。
- **reason 小字**：失败或阻塞任务附一行 sans 小字解释"为什么"，让用户理解阻塞的因果链（02 失败 → 03 阻塞 → 04 阻塞）。**只在非成功状态显示**，成功不加噪音。
- **正文与摘要严格分离**：矩阵上方只渲染安全完成的任务正文（01、05），失败/阻塞任务**不生成伪正文**——这是可信度的核心。

> **实现演进**（`TaskStatusSummary.vue` + `taskReasonLabels.ts`）：原型初稿的 reason 是后端返回的自由文本。Spec §16 明确「公开 API 只返回白名单原因码，不得把异常消息/堆栈写入响应」。实现据此改为**前端硬编码白名单映射**——后端只返回闭集原因码（`PORTFOLIO_EVIDENCE_INSUFFICIENT` 等），前端 `taskReasonLabels.ts` 把码映射成预定义中文短语，未知码一律回落克制通用句，**永不展示原始码或异常文本**。这是「人话解释」与「不泄露内部细节」的折中。此外，有 `blockedByDisplayIndexes` 时优先点名依赖（「依赖任务 02、03 未完成」），比泛泛「依赖未满足」更精确。

#### 3.3.5 Plan Invalidated Notice · 计划失效提示（状态 G）

```
┃ 计划已失效 ┃
│ 原计划需要重新生成                    │
│ 你之前确认的计划已经过期，我不会沿用  │
│ 旧的继续，也不会自动替换。请确认是否  │
│ 重新生成。                            │
│ [重新生成计划]  暂不处理              │
└───────────────────────────────────────┘
```

- 红边框 callout，复用 `.problem-callout`。
- **明说不静默替换**：文案明确"不会沿用旧的继续，也不会自动替换"——这是与"静默重路由"的关键对立。
- **两个出口**：`重新生成计划`（发 `REGENERATE_PLAN`）+ `暂不处理`（dismiss，保留现状、不清除上下文）。

> **实现演进**（`PlanInvalidatedNotice.vue`）：原型初稿二号按钮叫「取消」，实现改为「暂不处理」——失效后没有"取消"语义（计划已失效，无所谓取消），只有"现在不处理"。失效原因由后端 `planChange.summary` + `changeLabels` 提供受控文案。同样补充 `readonly` 态（被后续轮次取代时只读）。Spec §11 定义了 6 类失效原因码与对应行为（重签 / 完全重规划 / 拒绝），前端不暴露这些码，只展示受控文案。

| 语汇 | 用途 | 复用来源 |
|---|---|---|
| `↳` 前缀 | 建议问题、依赖指向、阻塞下游 | `.dynamic-suggestions::before` |
| `[E001]` 引用按钮 | 章节级、消息级证据入口 | `.answer-block__citations` |

## 4. 八个状态的完整说明

### 状态 A · 简单单任务直接回答

- **触发问题**：`介绍 SQL 审计项目的实现方案。`
- **UI 组成**：用户消息 + Agent meta（已核验标签）+ structured-answer（标题 + 摘要 + 一个章节 + 证据入口 + 建议问题）。
- **计划 UI**：**完全不出现**。无计划卡、无摘要条、无步骤列表。
- **设计意图**：验证"单任务体验没有被计划 UI 打扰"。简单任务直接给答案，不要用流程化的东西打断阅读。
- **退出**：无（终态回答）。

### 状态 B · 多任务自动执行（≤3 任务）

- **触发问题**：`介绍 SQL 审计和 ABTest 项目，再比较它们。`
- **UI 组成**：三个 `.answer-block`（介绍 A / 介绍 B / 比较）+ 折叠摘要条。
- **计划 UI**：一条折叠摘要条，默认 `data-open="false"`，显示 `介绍 → 比较 → 推荐 · 3 步已完成`。点击展开看完整任务清单。
- **顺序固定**：任务清单按计划顺序（01→02→03）显示，**不随并行完成顺序变化**。
- **设计意图**：验证"多任务摘要不取代正常回答正文"。正文是三个完整 block，摘要是底部一条可折叠条，互不遮挡。
- **交互**：摘要条点击折叠/展开（chevron 旋转）。

### 状态 C · 复杂计划等待确认（5 步）

- **触发问题**：`分别介绍 SQL 审计和 ABTest，比较它们，再根据比较推荐一个适合后端面试展示的，并总结展示策略。`
- **UI 组成**：Agent meta（待确认标签）+ 标题 + 摘要 + 约束条 + 计划卡（5 步清单 + 依赖标注 + 三选一）。
- **约束展示**：`后端 · 面试展示 · 推荐 1 个` 置顶 mono 条。
- **依赖标注**：03 `↳ 需要 01、02 先完成`；04 `↳ 需要 03 先完成`；05 `↳ 使用 04 的结果`。不画连接线。
- **三选一**：`按此计划继续`（主按钮）/ `调整计划`（幽灵）/ `取消`（幽灵）。
- **设计意图**：验证"10 秒内理解复杂计划"。线性编号 + 一行依赖标注 + 约束置顶，无需翻页即可看全。
- **交互**：点 `按此计划继续` → 切换到状态 F 模拟执行结果（演示确认→执行的流向）。

### 状态 D · 局部澄清

- **触发问题**：`介绍 SQL 审计，再把它和另一个项目比较。`
- **UI 组成**：Agent meta（已核验 + 待澄清双标签）+ SQL 审计介绍正文（已继续）+ 澄清卡（局部变体）。
- **澄清卡**：红菱形问题 + 3 个候选项目 chip + `已继续` 条标明"介绍 SQL 审计不受影响"。
- **设计意图**：验证"局部歧义时明确任务可以继续，只澄清受影响的任务"。一次只问第二个主体，不让用户一次性回答所有问题。
- **退出**：用户点 chip 或建议问题选定第二个项目。

### 状态 E · 关键依赖澄清

- **触发问题**：`比较这两个项目，再推荐一个。`（无合法的"这两个"引用）
- **UI 组成**：Agent meta（待澄清 + 上游阻塞标签）+ 标题 + 摘要 + 澄清卡（关键变体）。
- **澄清卡**：红菱形问题 + 候选主体 chip + `被阻塞的下游任务` 列出比较 + 推荐两条阻塞链。
- **不执行**：比较和推荐都不执行，因为没有合法主体。
- **设计意图**：验证"上游关键歧义时先澄清主体，并展示被阻塞的下游任务"。明确不从历史正文猜测主体（隐私与可信度）。
- **退出**：用户选定两个主体。

### 状态 F · 部分成功

- **触发问题**：`介绍 SQL 审计和 ABTest，比较它们，推荐一个适合后端面试的，再讲讲通用面试技巧。`
- **UI 组成**：Agent meta（部分成功标签）+ 标题 + 摘要 + **安全正文（仅 01、05）** + 状态矩阵 + 证据 + 建议问题。
- **正文规则**：
  - 01 介绍 SQL 审计 → 渲染（作品集事实，附 `[E001]`）；
  - 05 通用面试技巧 → 渲染（通用知识，附 `.source-tag[data-source="GENERAL"]`，无证据引用）；
  - 02/03/04 → **不渲染任何正文**，只在状态矩阵里标明原因。
- **状态矩阵**：5 行，每行序号 + 任务名（失败/阻塞附 reason）+ 状态标签。
- **来源区分**：作品集事实 block 带 `.source-tag[data-source="PORTFOLIO"]`（红边），通用知识 block 带 `.source-tag[data-source="GENERAL"]`（灰边）。
- **设计意图**：验证"部分成功时同时表达成功、证据不足、依赖阻塞和通用解释"，且"正文与任务状态摘要分开，不为失败或阻塞任务生成伪正文"。

### 状态 G · 计划失效

- **触发条件**：此前确认的计划，contentVersion / integrityToken / expiresAt 失效。
- **UI 组成**：Agent meta（需重新生成标签）+ 标题 + 摘要 + 失效 callout（红边框）。
- **callout 文案**：明确"不会沿用旧的继续，也不会自动替换"，提供 `重新生成计划` / `取消`。
- **不展示**：不展示技术异常文案、不展示失效的具体原因（令牌过期 vs 版本不匹配）。
- **设计意图**：验证"计划版本或确认令牌失效时明确要求重新生成，不静默替换"。

### 状态 H · 全局安全边界

- **触发条件**：请求命中全局安全边界。
- **UI 组成**：Agent meta（已终止标签）+ 标题 + 摘要 + 边界 callout（左红线克制表达）+ 建议问题（引导回作品集范围）。
- **整轮终止**：不显示部分计划、不显示已执行的任务、不显示内部安全规则。
- **克制表达**：`这个请求我无法回答。如果你是在问作品集相关的...可以换个方式问。` 不解释为什么被拦截。
- **设计意图**：验证"全局安全边界命中时终止整轮，不显示部分计划"。

## 5. 信息架构原则

原型遵循五条信息架构原则，这些原则将延续到阶段二正式 Spec：

### 原则 1 · 正文与任务状态摘要分离

正文（`.structured-answer` 内的 `.answer-block`）只承载**安全完成的任务内容**。任务状态（成功/失败/阻塞）放在独立的摘要组件（折叠条或状态矩阵）里。

**推论**：失败或阻塞的任务**绝不生成伪正文**。状态 F 里 02/03/04 没有任何正文 block，只在矩阵里出现。这是可信度的核心——不为凑完整性而编造内容。

### 原则 2 · 密度跟随复杂度

| 任务复杂度 | 计划 UI 密度 | 状态 |
|---|---|---|
| 单任务 | 无 | A |
| ≤3 任务自动执行 | 折叠摘要条 | B |
| ≥复杂阈值待确认 | 完整清单 + 三选一 | C |

简单任务不被计划 UI 打扰，复杂计划给足信息让用户决策。同一个组件（编号线性清单）通过"不渲染 / 折叠 / 展开"覆盖三种密度。

### 原则 3 · 来源可区分

作品集事实（`PORTFOLIO`）和通用知识（`GENERAL`）必须可区分：
- scope 标签：`作品集资料` / `通用知识`；
- `.source-tag`：红边（作品集）/ 灰边（通用）；
- 证据引用：作品集事实附 `[E001]`，通用知识无证据引用。

**推论**：`SYNTHESIS` 来源域（如"总结展示策略"）保留独立来源标记（灰边「综合结论」），与作品集事实、通用知识三分；Spec §13.3 还要求综合结论保留完整上游 provenance，不新造证据。详见 §9.3。

### 原则 4 · 确认与澄清语义区分

| | 确认（Confirmation） | 澄清（Clarification） |
|---|---|---|
| 语义 | 计划已成型，等用户放行 | 缺信息，无法生成/继续 |
| 视觉 | 实底红标签 + 三选一按钮 | 红边标签 + 候选选项 chip |
| 用户动作 | 继续 / 调整 / 取消 | 选一个 / 自由输入 |

两者都是"需要用户行动"，但语义不同，视觉语法明确区分，不让用户混淆。

### 原则 5 · 不泄露内部细节

以下内容**绝不**对用户可见：
- 模型思维过程、Prompt；
- 内部工具参数、检索评分、异常堆栈；
- 安全规则细节、边界判定逻辑；
- 任务 ID、依赖类型枚举、完整性令牌（这些是契约字段，不是用户界面元素）。

`demo-rail` 是评审控件，非产品 UI，原型里明确标注"非生产代码"。

## 6. 交互流程

> 下面的流程已对齐前端实际实现（`AgentWorkspace.vue` 的 `confirmSemanticPlan` / `adjustSemanticPlan` / `selectClarification` / `regenerateSemanticPlan`）。原型初稿措辞与实现有出入处，已在各流程下标注。

### 6.1 主流程：复杂计划确认 → 执行

```
用户提问（复杂）
    ↓
Agent 生成 SemanticTurnPlan（5 步）
    ↓
 disposition = CONFIRMATION_REQUIRED → 展示计划卡（状态 C）
    ↓
 用户三选一：
 ├─ 按此计划继续 → 发 CONFIRM_PLAN + 确认信封 → 执行 → 结果（成功 B / 部分成功 F）
 ├─ 调整计划    → 聚焦输入框（见下注）→ 用户手输调整 → 发新 ASK → 新计划卡
 └─ 取消       → 清除 tab memory 中的确认信封，不执行
```

> **实现演进 · 调整计划**：原型流程图写「→ 生成新计划 → 回到确认」，暗示自动动作。Spec §10.3 明确「调整计划提交新的 ASK 与自然语言调整，不允许前端直接编辑内部图」。实现据此：点「调整计划」只聚焦 composer 输入框（`adjustSemanticPlan` → `textarea.focus()`），等用户手输调整意图后提交新 ASK，后端重新路由生成新计划。原计划卡在调整期间进入 `adjusting` 态（仍可确认），用户也可放弃调整直接确认原计划。
>
> **实现演进 · 确认安全**：`confirmSemanticPlan` 在提交前校验 `pendingConfirmation.confirmationId === confirmation.confirmationId`，前端层防篡改/防过期信封误用。

### 6.2 澄清流程

```
用户提问（含歧义）
    ↓
 Agent 判断歧义类型：
 ├─ 局部歧义（D）：安全任务继续，只澄清受影响任务
 │     ↓ 展示已继续正文 + 局部澄清卡
 │     ↓ 用户选定 → 注入 semanticContext.activeSubjects → 发新 ASK → 后端重新路由
 └─ 关键歧义（E）：整链阻塞，先澄清主体
       ↓ 展示关键澄清卡 + 被阻塞下游
       ↓ 用户选定主体 → 注入 activeSubjects → 发新 ASK → 重新路由 → 确认/执行
```

> **实现演进 · 澄清提交**：原型写「继续执行受影响任务」，措辞像接着原计划跑。实现里 `selectClarification` 把选中值注入 `semanticContext.activeSubjects`，然后发**全新一轮 ASK**（带原始 question + enriched context），后端重新路由——可能生成新计划，也可能直接执行。澄清本质是"补全信息后重新理解需求"，不是续跑。
>
> **铁律（保留）**：不从历史回答正文推断主体。状态 E 即便对话历史里出现过项目名，也不自动用作"这两个"的指代——必须用户明确指定。

### 6.3 失效流程

```
计划执行中 / 确认后
    ↓
 确认时按固定顺序验证：签名 → schema → expiresAt → contentVersion → 主体 → capability
    ↓
 失效 → 展示失效 callout（状态 G）—— 不静默重路由
    ↓
 用户：重新生成（REGENERATE_PLAN + invalidatedPlanReference）/ 暂不处理（dismiss）
```

> **实现演进**：Spec §11 把失效细分为 6 类原因码（完整性无效 / schema 不支持 / 仅确认过期 / 内容版本变 / 主体失效 / 能力集变），对应「拒绝只能重问」「完全重规划」「同计划重签」三种行为。前端不暴露这些码，只展示后端 `planChange` 受控文案；用户侧只见「原计划已失效 + 重新生成/暂不处理」。

### 6.4 边界流程

```
请求命中全局安全边界
    ↓
 整轮终止（状态 H）—— 不显示部分计划、不显示已执行任务
    ↓
 展示克制表达 + 引导回作品集范围的建议问题
```

## 8. 可访问性

- **键盘可达**：所有交互元素是原生 `<button>`，Tab 可达，Enter 触发。
- **焦点可见**：`:focus-visible` 红色 outline + 3px offset。
- **ARIA**：`demo-rail` 用 `role="tablist"`，状态按钮用 `role="tab"` + `aria-selected`；折叠摘要条用 `aria-expanded`。
- **reduced motion**：`@media (prefers-reduced-motion: reduce)` 禁用所有 transition / animation。
- **颜色对比**：正文 `--ink #201c17` on `--agent-thread-paper #f5e8d1`，对比度 > 12:1；mono 小字 `--muted #746b5e` 对比度 > 4.5:1。

## 9. 原型提出的待定项 · 解决情况

原型阶段提出的四个待定项，现已在 Spec 与实现中全部解决。下表对照「原型待定 → 最终决策」：

### 9.1 任务上限 / 确认阈值 — ✅ 已解决

- **原型待定**：纯任务数，还是成本 + 冲突 + 扩范围综合判定？
- **Spec 决策**（§2.1 第 8 条、§10.1）：1–3 个简单任务自动执行，4–6 个任务或任一确认触发项要求确认，超过六个任务要求拆分。即**任务数为主、确认触发项为辅**的综合判定。

### 9.2 状态摘要折叠密度 — ✅ 已解决

- **原型待定**：部分成功时折叠态要不要显示失败计数？
- **Spec 决策**（§15.3）：要。折叠态显示 `2/5 完成 · 1 证据不足 · 2 阻塞`。
- **实现**（`CompactTaskSummary.vue`）：采用折中——全成功用流程箭头、部分成功用计数 + 异常摘要，部分成功时首屏自动展开。

### 9.3 来源区分粒度 — ✅ 已解决

- **原型待定**：`SYNTHESIS` 是否单独标记？
- **Spec 决策**（§13.3、§15）：`SYNTHESIS` 保留独立来源域，与 `PORTFOLIO` / `GENERAL` 三分。前端来源标签三档：作品集资料（红边/红字）/ 通用知识（灰）/ 综合结论（灰）。Spec §13.3 还要求 `SYNTHESIS` 保留完整上游 provenance（`derivationType` / `originDomains` / `sourceTaskIds` 等），不新造证据。

### 9.4 计划失效触发 — ✅ 已解决

- **原型待定**：哪个字段是主信号？重新生成是复用还是重规划？
- **Spec 决策**（§11）：按固定顺序验证签名 → schema → expiresAt → contentVersion → 主体 → capability，**逐项对应不同行为**——仅过期则同计划重签，内容/主体/能力变则完全重规划，完整性失败则拒绝只能重问。无单一"主信号"，按失效类型分流。
