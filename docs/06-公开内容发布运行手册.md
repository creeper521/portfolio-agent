# 公开内容发布运行手册
<!-- DOCUMENT_STATUS: CURRENT_AUTHORITY -->

> **适用合同：** 当前 schema `4.0` 公开发布合同
> **包形式：** 七文件原子 Bundle
> **入口：** `scripts/portfolio-governance.ps1`
> **边界：** 发布工具不自动审批、不自动串联阶段、不重启应用；生产部署和进程管理由部署环境负责。

## 角色与目录

至少分离：

- 候选准备者：只能生成公开候选；
- 人工审核者：核对 review pack、隐私、Claim/Evidence 和 Preset；
- 发布操作者：持有 release root 写权限并显式执行发布或回滚；
- 应用：只读 active release，不读取 governance workspace。

`Workspace`、候选目录、模型目录与 `ReleaseRoot` 必须位于 Git 工作树外。工具拒绝 traversal、symlink、junction 和不安全路径。不要在命令、日志或聊天中打印私有绝对路径。

建议 release 结构：

```text
<release-root>/
├─ active
├─ versions/
│  └─ <contentVersion>/
└─ blocked-versions.json
```

`active` 是只包含 contentVersion 的指针文件；版本目录不可变。

## 当前发布流水线

阶段必须按顺序人工推进：

```text
prepare candidate
→ inspect
→ validate
→ benchmark
→ build-review-pack
→ human review
→ approve
→ publish dry-run
→ publish -Confirm
→ verify
→ deployment-owned restart/readiness/browser checks
```

任何 BLOCKER、ERROR、隐私异常、引用异常、基准缺口或输入指纹变化都会中断流水线。不得跳过、自动批准或复用已经 stale 的 Approval。

## 候选准备

当前 retrieval 候选的 canonical payload 是：

```text
candidate/
├─ portfolio.json
├─ presentation.json
└─ rag-documents.jsonl
```

候选不能携带 `manifest.json`、`checksums.json`、`keyword-index.json` 或 `vector-index.bin`。RAG 文档必须先由受控构建入口从同一公开事实复现；不得调用外部 Embedding Provider。

候选生成和 decision ledger 属于私有治理流程。所有源路径、审核内容和原始 Evidence 保持在仓库外。

## 通用命令形式

所有治理命令通过仓库包装器执行：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/portfolio-governance.ps1 -Command <command> -Workspace <private-workspace>
```

当前主要命令：

- `inspect`：验证工作区入口，不读取或改变 active；
- `validate`：校验候选、ledger、closed schema、引用、隐私和输入指纹；
- `benchmark`：执行当前 Preset/安全/证据基准；
- `build-review-pack`：生成不含私有原文的人工审核包；
- `approve`：使用明确审核元数据生成 Approval；
- `publish`：验证 Approval 并准备 release；无 `-Confirm` 时是 dry-run；
- `verify`：验证指定 release root 的完整性；
- `list`、`status`：只读查看版本与 active；
- `rollback`：默认 dry-run，显式确认后切换到已验证版本；
- `case`：记录脱敏的发布故障处理状态。

`validate`、`benchmark`、`build-review-pack`、`approve`、`publish` 与 `verify` 都要求同一 decision ledger。候选或 ledger 任一字节变化都会形成不同输入指纹，旧审核和 Approval 失效。

## Validate

Validate 至少执行：

- 候选文件白名单与路径安全；
- JSON/JSONL closed schema；
- schema/content version 一致性；
- Project、Case、Collection、Claim、Evidence、Timeline 与 Preset 引用闭合；
- Project/Case 主体与 Claim/Evidence 支持边界；
- Evidence 必须已批准且原文保持私有；
- decision ledger 与公开候选一致；
- Preset contract policy、主体、required/supporting Claim 与 Evidence requirement；
- 隐私文本与被禁止 URL/精确指标扫描；
- canonical payload hash；
- 本地检索描述、RAG 文档与固定模型要求。

Validate 不创建 Approval、不写 release root、不切换 active。

## Benchmark 与 review pack

Benchmark 必须覆盖当前 ACTIVE Preset 的 supported question、alias、boundary、Claim/Evidence 和 safety 场景。基准引用只能指向本候选实际发布的 Claim 与 Evidence。

`build-review-pack` 输出脱敏摘要、Case、Claim、关联、隐私结果、benchmark 结果、checksums 和 approval request。它不包含原始 Evidence、私有 Markdown 或凭据。

审核者必须确认：

- 状态与贡献没有扩大；
- Case 限制、验证和结果表达准确；
- Claim 有合适 Evidence 支持；
- Preset 文案、主体和预期回答一致；
- DRAFT Preset 不会作为 ACTIVE 操作入口；
- review pack 的指纹与准备审批的运行一致。

## Approve

Approve 需要明确提供 ReviewRunId、ApprovedBy、PrivacyReviewId、BenchmarkRunId、Candidate 与 DecisionLedger。

工具验证 review run 的 candidate payload、ledger、Preset set、policy、benchmark、工具版本、编译器和模型身份均未变化，再生成带 digest 的 Approval。Approval 只绑定本次精确输入，不是对未来同名版本的授权。

## Publish dry-run

在任何 active 变化前先运行 publish dry-run：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/portfolio-governance.ps1 -Command publish -Workspace <private-workspace> -Candidate <private-candidate> -DecisionLedger <private-ledger> -ApprovalId <approval-id> -ReleaseRoot <release-root> -JarPath backend/target/portfolio-agent.jar -ModelDirectory <verified-local-model>
```

即使是 dry-run，retrieval publish 也会使用固定本地模型复现 canonical RAG、临时派生 keyword/vector index 并校验输出；临时目录随后删除。此步骤不会改变 active。

## Publish 确认

只有 dry-run 成功且操作者再次核对目标后，添加 `-Confirm`。需要发布后 HTTP 探针时，通过 `-PostSwitchProbeUri` 传入部署方允许的 URI。

确认发布依次：

1. 重新验证候选、ledger 和 Approval；
2. 逐字节复制 canonical payload；
3. 复现 RAG 并派生 keyword/vector index；
4. 生成 checksums 与 manifest；
5. 将完整临时目录原子移动为不可变版本目录；
6. 原子替换 active 指针文件；
7. 写入不含敏感正文的审计记录；
8. 若配置了 post-switch probes，逐一验证。

相同 contentVersion 已存在时，只有 payload 与 ledger 完全一致才允许幂等通过；不同字节或 ledger 是版本冲突。

发布工具不负责重启 Java、systemd 或容器。未传 probe 时，操作者必须在部署层完成重启与验证；不得把“active 已切换”写成“应用已加载”或“生产已验收”。

## Post-switch probe 与自动恢复

配置 probe 时，发布前必须存在完整旧 active 作为 rollback point。任一 probe 非成功状态、超时或抛错时，工具原子恢复旧 active 并返回失败。

Probe 只能证明指定 URI 的即时响应；它不能替代应用已加载目标 contentVersion、Project/Case/Preset 内容与引用、packaged-JAR 浏览器路径、隐私检查或真实 Provider 验收。这些证据由部署和发布验证流程另行留存。

## Verify、status 与回滚

发布后运行只读命令核对 versions、active、manifest、checksums 与阻断清单。应用实际加载版本还要通过应用 readiness 或公开内容响应单独核对。

回滚前验证：

- 目标版本存在且七文件完整；
- checksums、manifest 与应用兼容性通过；
- 目标未进入 blocked versions；
- 当前没有冲突发布；
- 回滚理由明确；
- dry-run 已成功。

显式确认后只原子切换 active；部署方负责重启和 HTTP/浏览器复验。含不应再次公开内容的版本应加入 blocked registry，不能通过普通 publish/rollback 重新激活。

## 本地 PostgreSQL 投影

将随包内容导入本地公开数据库使用 `scripts/postgres-local.ps1`，与服务器 release 发布是不同操作：

- `verify-public-bundle`：只验证随包 Bundle；
- `import-public`：创建不可变数据库 release；
- `activate-public`：需要相同 ReleaseId 的二次确认；
- `verify`：检查三个本地数据库与 active 投影。

数据库导入不能替代 canonical release、Approval 或七文件校验。治理 Markdown 命令只作用于私有 governance database，普通应用启动不会触发导入。

## 发布后的最小验收

部署方至少验证：

- readiness 成功且加载目标 contentVersion；
- 首页与静态资源可访问；
- `GET /api/v1/public-content` 返回目标公开内容；
- 一个 Project、一个 Case 和一个 ACTIVE Preset 的公开路径正确；
- 未知主体失败关闭；
- Agent 确定性路径只引用当前 release；
- 页面和响应不含路径、主机、凭据或私有字段；
- 回滚点仍可验证。

真实 Provider 不是内容发布的隐式步骤。需要将其作为发布 Exit Gate 时，必须显式授权并单独运行 provider canary。

## 安全撤回

发现公开内容越界时：

1. 停止继续发布；
2. 切回已验证旧 release 或发布修正版；
3. 阻断问题版本；
4. 保存脱敏故障记录；
5. 处理 CDN、缓存和外部副本；
6. 修复候选、ledger、Approval 与回归基准后再进入完整流水线。

不得直接修改版本目录、数据库 active 行或私有治理审计来“快速修复”。
