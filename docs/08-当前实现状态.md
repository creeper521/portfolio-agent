# 当前实现与未实现功能盘点

> **状态：** 当前实现盘点（以生产代码、配置、自动化测试和发布脚本为证据）
> **核对日期：** 2026-08-12
> **代码基线：** 本地 `master`（阶段 2 统一语义路由、无状态推荐与公开 Selection HTTP 收口已完成验证）
> **维护规则：** 功能合入、默认开关或产品边界变化时，同步更新本文与 `00-文档状态索引.md`。

## 1. 结论

当前项目已经从“一个确定性问答的 V0”扩展为一个可打包交付的公开实习作品集 Agent：前端具备八个正式路由、独立 Case 体验和页面内存工作台，后端具备公开内容 API、P3 唯一确定性只读执行内核、强类型短期业务 Context、严格回答契约、内容治理、可选模型能力、本地混合检索、显式引用式多轮，并提供单 JAR、Docker 与完整发布门禁。

Case 后端与发布前五项收尾已经完成：`source=CASE`、Project/Case 互斥、未知公开主体 fail-closed、真实随包 Bundle 集成、Case API/v2 JAR 冒烟，以及显式 `-RequireLiveProvider` 响应门禁均已有实现和自动化测试。普通 CI 强制关闭模型调用；真实 Provider 外部调用仍需在获批生产候选环境单独留证。

但它仍不是完整 V1。独立 `/cases`、`/cases/:slug`、规范重定向、具体 UI、Case → Agent 页面内存交接和 packaged-JAR 浏览器联调均已完成；故事页属于后续 selected-case 增强。模型表达、本地检索以及 PostgreSQL/pgvector 数据源默认关闭，真实 Provider 与生产环境仍待验收。动态工具/插件、通用 Tool Registry、多 Agent、长期记忆、认证和私有 Copilot 均未实现；P3 PostgreSQL Context Store 是经批准的短期强类型业务 Context 例外。

内容准备层已经登记 72 项私有资产。历史 `2026-07-27.1` 批次完成过精确哈希 Approval 与本地发布；当前随包公开快照已经演进为 schema `4.0`、内容版本 `2026-08-04.2`，包含 6 个 Project、52 个 Case、3 个 Collection、83 个 Claim、63 个 APPROVED Evidence、83 条 Claim–Evidence 关联、83 个检索 chunk、12 条 TimelineEvent 和 19 个 QuestionPreset。7 项 `EXCLUDE` 继续保持私有。

当前公开版本已完成 Wave 1 的 Keyword、Vector、Hybrid 三路真实本地模型比较：37 个问题覆盖 Holdout、Regression 和 Calibration；策略 v2.1 的三路 false-sufficient 均为 0，Hybrid 在 26 个正例上取得 Hit@1 0.8846、Hit@5 1.0000、MRR@5 0.9359 和 20/26 正向充分判定。完整过程、v2 被拒原因与边界见 `docs/reports/retrieval-wave-1-policy-v2-1-2026-07-27.md`。运行时 Profile 未改变，检索仍默认关闭，也没有部署。

全量内容还完成了 89 例、267 次路由评估的真实比较：Hybrid 在 38 个正例上取得 Hit@1 0.9211、Hit@5 1.0000、MRR@5 0.9561 和 32/38 正向充分判定，明显高于 Keyword 的 13/38 和 Vector 的 17/38；三路 false-sufficient 仍为 0。该结果证明混合检索对扩充内容有价值，但不代表所有决策用例通过，详见 `docs/reports/retrieval-full-public-assets-candidate-2026-07-27.md`。

## 2. 已实现功能

### 2.1 公开作品集前端

- Vue 3 + TypeScript + Vite 单页应用，正式路由为 `/`、`/projects`、`/projects/:slug`、`/cases`、`/cases/:slug`、`/timeline`、`/evidence`、`/agent`，并有显式 404 页面。
- Case 目录按交付状态组织 49 个公开案例；详情页展示问题、动作、判断、验证、结果、边界、证据和建议问题，旧 `/projects/{caseSlug}` 会替换为规范 Case URL。
- Case → Agent 使用随机、短时、一次性页面内存 handoff；URL 立即清为 `/agent`，问题不进入浏览器历史或存储，Case 上下文可见、可清除，证据栏只展示当前 Case 的公开证据。
- 首页由公开数据驱动，包含作品定位、角色化提问、可信度摘要和探索入口；缺少姓名时不生成虚构占位内容。
- 项目目录、项目详情、时间线和证据中心均从 `GET /api/v1/public-content` 聚合接口读取，同一次加载共享请求，并提供 loading、空状态、失败重试和未知资源状态。
- Agent 三栏工作台包含会话栏、对话区和证据区；桌面端支持可拖动/键盘调整分栏，窄屏改为抽屉且避免水平溢出。
- Agent 工作台采用当前 B 暖调作品窗口：深色顶部导航、暖调中栏、牛血红 CTA 与响应式圆角外壳；宽屏三栏、窄屏按断点收为证据与会话抽屉。A「均衡纸阶」仅保留为历史视觉前序。
- 首页到 Agent 使用随机、短时、一次性内存 `handoffId`；问题和回答不进入 URL 或浏览器历史。
- 会话、消息、失败重试状态和引用上下文只存在当前页面内存；刷新或关闭页面后消失，不使用 localStorage、sessionStorage 或服务端持久化。
- 回答 UI 区分 `ANSWERED / NEEDS_CLARIFICATION / NOT_SUPPORTED / CAPABILITY_UNAVAILABLE / REJECTED`，并分别展示回答范围、构造方式、意图来源、证据状态、结构化 section、证据引用、建议问题与内容版本变化提示；页面布局和既有视觉骨架没有改变。
- Agent 会话标题保存首个问题的完整规范化文本，数据层不截断；主标题最多两行、侧栏单行仅视觉省略，悬停与屏幕阅读器可读全文，手动重命名后永久锁定自动标题。
- 每个会话独立维护 `coveredTopics` 对话进度并随下一轮请求回传，成功响应后整体替换，重试使用失败当时的快照，多会话互不污染。
- 每条回答固定展示自己的三个引导问题，按 `guidanceStage` 分配当前项目与其他项目比例，点击后携带其 Project/Case 目标上下文；契约异常时从公开问题预设确定性补足，恢复诊断只记录错误类别、数量和阶段。
- 能力降级作为正常响应展示安全回答、降级提示和引导问题，可连续对话；仅传输失败进入重试视图，并同时提供三个本地公开问题。
- 对话消息可展示后端返回的结构化 `portfolioRecommendation`；前端按后端既定顺序渲染并在当前标签页内原样回传推荐上下文，刷新、关闭页面或新建会话后清空，后端每次重新校验。

### 2.2 公开内容与 API

- Spring Boot 提供 `GET /api/v1/portfolio`、`GET /api/v1/projects/{slug}`、`GET /api/v1/cases`、`GET /api/v1/cases/{slug}`、`GET /api/v1/public-content` 和 `POST /api/v2/answers`。`/api/v2/answers` 是唯一公开 Agent 回答入口；`POST /api/v1/answers` 与独立 Selection HTTP 接口均已删除并返回 404。
- `POST /api/v1/client-diagnostics` 是只读公开端点的唯一例外：默认关闭，只接受封闭、限流且
  不持久化的诊断事件契约；永不接受访客内容、任意元数据、原始堆栈、URL、Headers、请求体、
  响应体、原始来源地址或凭据。
- 当前随包公开快照为 schema `4.0`、内容版本 `2026-08-05.1`，包含 6 个 Project、52 个 Case、3 个 Collection、88 个 Claim、63 个 APPROVED Evidence、88 条 Claim–Evidence 关联、88 个检索 chunk、12 条 TimelineEvent 和 19 个 QuestionPreset（18 个 ACTIVE Contract + 1 个跨主体 DRAFT）；7 项 `EXCLUDE` 保持私有。
- 已实现独立不可变 CaseStudy 领域模型、CaseType、CASE Claim 归属与引用校验、只读服务和公开 DTO；未知 Case slug 返回 404 `CASE_NOT_FOUND`。
- 加载器显式接受 schema 2.0/3.0：2.0 被规范化为空 `cases`/`caseIds`，3.0 严格校验 Case 集合与引用，未知版本和缺失必填集合失败关闭。
- `GET /api/v1/public-content` 新增 `cases`、`caseSlugsByEvidenceId`，QuestionPreset 与 Timeline 投影新增 `caseSlugs`；公共 DTO 只输出 `ACTIVE` 的正式 preset，并携带 `contractVersion` 与 `availability=ACTIVE`，跨主体 Draft preset 不再进入公共推荐区。
- 已实现 Preset Contract 治理闭环：`preset-contract-policy.v1.json` 精确声明 18 个单主体 Active Contract 与 1 个跨主体 Draft；候选准备时从 policy 确定性投影 `contractSubjectId`、Required/Supporting Claims、Evidence Requirement 与状态，并计算单项 `pcv1-*` 版本与 Active 集合 `sha256:*` 指纹；`validate / benchmark / build-review-pack / approve / publish / verify` 全程重算并比对指纹，旧基线重生成、缺字段、Active 集合漂移与 hash 漂移均阻断发布。运行时 `QuestionDefinition.contractSubjectId` 是执行主体唯一来源，DRAFT 不再进入 runtime questions 与公共 DTO。
- 结构化主体只表示检索范围，不再自动等价于意图：`StructuredSubjectResolver` 在规则与模型分类之前按 slug 校验主体唯一性并返回已验证 `subjectId`，未知/重复 slug 返回 `INVALID_INPUT + STRUCTURED_SUBJECT_INVALID`；模型能力允许时，普通结构化主体自由问题仍进入模型任务分类并保留主体约束，模型关闭时回退到确定性 `FACT_LOOKUP`（`SUBJECT_SCOPED_RELEVANCE`）；模型与 Embedding 默认关闭时，正式 preset 与带公开主体的 suggestion 仍可执行。
- `source=CASE` 时 Project/Case 主体互斥，未知主体 fail-closed，Case 不会隐式扩展为相关 Project；共享目录模型和详情投影已实现。
- 公开 DTO 与内部领域对象分离；启动/加载阶段校验 schema、唯一性、交叉引用、Evidence 审批状态、原始内容暴露标志和 Claim 验证约束。
- SPA 正式路由由单 JAR 回退到 Vue 入口，同时不吞掉 API 和静态资源路径；异常响应不暴露堆栈、本地路径或内部错误信息。

### 2.3 回答运行时与可信边界

- 每次回答基于一次不可变公开内容快照和匿名 `requestId`；访客问题和回答不写日志、不持久化。
- P-1 行为热修已收紧确定性兜底：纯数字、纯符号和 Emoji 等无法形成任务的输入进入既有安全澄清，不再伪装成通用概念解释；自然语言通用解释路径保持不变。
- 最终 HTTP 响应仅在 `ANSWERED` 或 `PARTIALLY_ANSWERED` 时投影回答 blocks、Evidence 与公开来源目录；澄清、边界、能力不可用和 `NOT_SUPPORTED` 均不携带这些内容。
- `GET /api/v1/public-content` 返回 `Cache-Control: no-store`，避免浏览器或中间层缓存已审阅公开内容快照。
- `TurnRouter` 是一轮语义解释的唯一权威；它先处理全局边界、结构化主体与正式预设，再使用高精度规则和可选闭集模型分类，产出一张经过校验的 `SemanticTurnPlan`。`PortfolioIntelligence.resolveTypedTask(...)` 只执行已分类的 Portfolio 任务，不再重判整轮意图。
- v2 请求支持可选 `questionPresetId` 与显式 `PortfolioReferenceContext`。API 强制校验主体、问题长度、媒体类型和引用范围；历史问答正文不能进入引用契约。
- 最终响应分别表达 `resolution`、`answerScope`、`constructionMode`、`intentSource`、`evidenceState`、`degraded` 和 `noticeCode`，避免把“模型参与”“检索命中”误标成“证据已验证”。
- 作品集智能诊断只记录封闭枚举、计数和耗时档位，不记录问题正文、回答正文、检索词项或 Provider 载荷。

### 2.10 阶段 1：单主体事实回答结构化编排

- 单主体作品集事实回答（`ANSWERED + FACT_LOOKUP + 单主体`）由确定性 `DeterministicPortfolioAnswerComposer` 组织为背景、职责、方案、验证、状态、边界章节；Comparison、Recommendation、澄清和失败响应保持原有路径，不调用大模型、不改变意图路由、不接入工具循环。
- `PortfolioRetrievedPassage` 携带完整、已验证的 `AnswerClaimProjection`（category、statement、detail、achievementStatus、contributionType、verificationBasis、verificationStatus、materiality、topics 与直接 Evidence ID）；Claim 非 `VERIFIED`、Evidence 非 `APPROVED`、Claim ID 为空或直接证据集合不一致的输入被拒绝。Bundle 与 PostgreSQL 双路径输出同一投影；PostgreSQL 通过 `V4__claim_answer_projection.sql` 保存新语义，历史行保持 NULL 不伪造。
- `AnswerFocus`（`OVERVIEW`/`FOCUSED`）只携带结构化请求类别，不含问题原文；`PortfolioIntelligenceResult` 贯穿 Focus。OVERVIEW 生成 lead Summary 并输出有证据的章节；FOCUSED 无 Summary、直达请求类别章节并提高预算；部分目标缺失时用受控缺口文案汇总到唯一 Boundary 章节（保留全部边界事实、不重复），缺口不虚构 Evidence；全部缺失由现有 `NOT_SUPPORTED + INSUFFICIENT` 语义处理。
- Composer 只消费 `AnswerFocus` 与已验证 Claim，不读取用户原文、不调用模型/网络/数据库/工具；确定性输出可复现：按 Claim ID 去重、同正文合并 Claim/Evidence ID、检索顺序稳定、章节顺序固定。数据或 Plan 不变量损坏（含 Plan 越界引用、事实章节无 Evidence、任何非法输入）时丢弃整个 Plan，返回 `CAPABILITY_UNAVAILABLE + INSUFFICIENT`、`degraded=true` 与 `ANSWER_COMPOSITION_INVALID`。
- v2 Block 增加可选 `sectionType`/`title`（新事实章节必须填写），`ConversationAnswerResult/Response` 增加可选 `summary`；Domain→DTO 映射编排收口到 `answer.mapper`，DTO 构造器只接收原始字段；后端只发布增强后的 v2 Blocks，legacy Sections 仅由前端映射层读取。
- 前端在 `mapAnswerResponse` 中把 v2 Blocks（优先）与 legacy Sections（兜底）映射为唯一 `AnswerSectionView[]`，`MappedAnswer` 不再暴露 raw blocks；顶层 Evidence 集合始终从统一 Sections 推导，章节内 Evidence 稳定去重；无类型旧 Block 按 resolution 区分兼容类型（ANSWERED 映射 GENERAL，非 ANSWERED 映射 BOUNDARY），不误标未迁移的 Comparison/Recommendation 回答；typed Block 缺 `sectionType`/`title` 时先上报脱敏诊断（`ANSWER_BLOCK_INVALID`）再拒绝整条响应；ConversationThread 与 Evidence Desk 只消费统一 Sections，回答级只展示一次作品集范围，引用按章节聚合。
- Category↔Section 映射由单一 `AnswerSectionMapping` 权威定义，Composer 章节归属与 Retrieval Planner 检索候选共用，避免新增分类时两处漂移。
- Eval 的“语义章节”改为按真实 typed sections 统计，新增 typedSectionCount/untypedBlockCount/sectionOrderValid/summaryPresent 指标；HTTP 评测客户端解析可选 `sectionType`/`title`/`summary`；JSON 报告导出新指标。
- 本阶段不默认启用 Provider、ONNX 或 PostgreSQL；`MODEL_GROUNDED`、`HYBRID`、`MIXED` 与多主体 Comparison Plan 未实现。

### 2.4 A/B：运行时可信度与内容治理

- 提供内容治理、检索 bundle 构建、静态 bundle 校验、架构、代码质量、隐私、JAR E2E 和完整 release verification 脚本。
- 内容发布 runbook 覆盖仓库外候选内容、人工 Approval、dry-run、发布、验证和回滚；bootstrap bundle 仅是开发/首装种子，不等价于生产人工审批。

### 2.5 C1：受控模型能力

- 支持 DeepSeek V4 Flash 与 GLM-4.7；每个部署只能显式选择一个 Provider，不重试、不跨 Provider 故障转移。
- 旧 `AnswerPlan` / Model Expression 独立回答链已删除。模型只承担受约束作品集分类、通用对话或基于已验证公开材料的表达；作品集事实、证据、推荐集合和排序仍由 `PortfolioIntelligence` 决定。
- Prompt 和输出校验禁止把检索词项、向量、工具内部数据、请求标识或历史回答正文发送给外部 Provider；Provider 输出为空、超长、结构非法或缺少公开引用时失败关闭。
- 默认 `PORTFOLIO_MODEL_ENABLED=false`；还必须同时具备数据策略批准和所选 Provider 密钥才会启用。Provider 可用性被显式注入决策，不能通过异常猜测能力状态。
- `scripts/start-local.ps1` 只接受仓库外绝对 Secret 路径，预检 AI 配置、Java 21、Maven、Node、前端依赖和端口；`-EnableGeneralAi` 显式启用语义路由与通用问答 operation，但不连带启用作品集表达或跨域表达。Live Provider 探针统一由 `scripts/provider-probe/invoke-live-provider-probe.ps1` 提供固定无主体 canary（不携带 Project/Case/Preset/Reference/Recommendation 上下文）；当前通用链只有在 canary 返回 `answerScope=GENERAL`、`intentSource=RULE`、`constructionMode=GENERAL_MODEL`、`evidenceState=NOT_REQUIRED`、`degraded=false`、`resolution=ANSWERED` 且包含回答块时才报告 `AI_CONNECTED`。根目录 `.env` 不会被隐式加载。

### 2.6 C2a：本地公开检索

- 已实现 BGE-small-zh-v1.5 INT8 ONNX 本地 Embedding 适配器、固定模型描述与哈希验证；模型文件不进入 Git，也不会在应用启动时下载。
- 发布期生成文档向量；运行期访客查询只在本机向量化。检索链路包含 query normalization、BM25、向量召回、RRF 融合和 Grounding Gate。
- `DISABLED` 为默认配置；支持显式 `KEYWORD_ONLY` 诊断模式和 `HYBRID` 模式。Hybrid 查询向量失败时可降级为关键词候选，但仍必须通过 grounding 校验。
- 自由问题只有在 Claim、Evidence、主体范围、阈值和上下文预算全部满足时才返回 `ANSWERED + VERIFIED`；证据不足返回 `NOT_SUPPORTED + INSUFFICIENT`，空证据不会被包装成回答。
- 已实现独立离线比较器和真实模型 CLI，可在同一内容、Policy、模型与 fixture 上输出 Keyword、Vector、Hybrid 的稳定 JSON/Markdown；Wave 0 基线中三路 false-sufficient 均为 0。该离线 Vector 路线不是生产 `VECTOR_ONLY` Profile。
- 作品集智能检索装配在 `portfolio.database.public.enabled=true` 时将 PostgreSQL/pgvector 设为主检索，并在其抛出 `PortfolioRetrievalException` 时自动改用独立加载的随包 Bundle；该 fallback 不读取数据库支持的 `PortfolioKnowledgeGateway`，冷启动数据库不可用时仍可返回随包内容版本。降级结果固定标记为 `degraded=true` 与 `POSTGRES_RETRIEVAL_UNAVAILABLE`。数据库关闭或未配置时只暴露 Bundle 检索 seam，任一配置下外部只能注入一个 `PortfolioRetriever`。

- 旧 `ContextEnvelopeValidator`、`ToolPlanBuilder`、`ToolPlanExecutor`、`ToolPlan` 与 `FollowUpIntent` 执行框架已删除，不再拥有第二套作品集决策权。

### 3.1 Agent 生产可用性（2026-07-29）

- 服务端或浏览器持久会话；当前刷新即清空是明确隐私契约，不是遗漏。
- 访客反馈提交 API、反馈数据库、人工标注队列和线上学习流水线。

### 4.2 Agent 与扩展架构

- 动态 Tool Registry、动态插件安装/发现/热更新和第三方工具授权。
- 通用 Hook、Orchestrator、工作流 DSL、DurableTask、任务恢复、调度和队列。
- 多 Agent 协作、委派、共享记忆和 Agent 间通信。
- 自动 Provider 故障转移、负载均衡、多 Provider 并发、自动重试和动态模型发现。
- 长期记忆、向量数据库、知识图谱和对私有知识的 RAG。

### 4.3 平台与运营

- 业务数据库、缓存、消息队列、对象存储、认证授权和租户隔离。

## 5. 下一步优先级建议

## 6. 状态判定依据

- “已实现”要求生产代码存在，且至少有自动化测试、发布脚本或随包制品中的一种可验证证据。
- “部分实现”表示核心代码存在，但默认关闭、依赖仓库外制品/审批，或当前数据规模无法触发完整价值。
- “未实现”表示只有路线图/设计描述、只有领域占位类型，或当前没有可调用的生产链路。
- 历史实施计划中的未勾选框不自动构成当前待办；以本文、`00-文档状态索引.md`、当前生产代码和最新验证结果为准。
