## 2. 不可突破的既有边界

本路线图中的全部改造必须继续遵守当前公开作品集边界：

1. 运行时只读取已审核、已发布的公开 Bundle 或其受控公开数据库投影；
2. 不读取私有 Obsidian 知识库、候选材料、原始日报、凭据或未审核截图；
3. 工具保持只读，不引入任意主机、任意路径、任意 SQL 或动态外部发布；
4. 访客问题不落盘、不进入 URL、浏览器持久存储或长期服务端会话；
5. 模型不能扩大项目状态、个人贡献或生产效果声明；
6. 证据不足、主体无效、模型异常或工具异常时继续失败关闭；
7. 普通 CI 不调用真实外部 Provider，真实模型和数据库验收保持显式授权；
8. 不因本轮改造引入开放式 ReAct、多 Agent、持久任务或通用 Tool Registry。

## 3. 当前背景与核心问题

### 3.1 回答有证据，但缺少面向用户的表达编排

当前作品集主链路由 `PortfolioIntelligence` 完成决策与检索，再由 `PortfolioIntelligenceAnswerAssembler` 生成回答。对于普通证据型回答，`materialBlocks()` 将每个 `PortfolioRetrievedPassage` 一对一转换成 `ConversationAnswerBlock`。

这能保留 Claim 和 Evidence 身份，却把“检索材料的颗粒度”直接暴露成“用户回答的段落颗粒度”。前端又逐个 Block 展示来源标签和引用，因此出现：

- “作品集资料”重复出现；
- 多段内容语义相近但缺少主次和过渡；
- 背景、职责、技术方案、验证和当前状态没有形成稳定结构；
- 引用分散在每个短段后面，正文被证据按钮切碎；
- 回答虽然事实安全，但不像经过组织的完整答复。

根因不是单一 CSS 或文案问题，而是检索结果与最终回答之间缺少一个稳定的语义编排阶段。

### 3.2 确定性意图规则覆盖窄，不能承担完整语义理解

当前 `PortfolioTaskResolver` 使用 `containsAny` 识别“比较”“推荐”“做了什么”“怎么实现”等有限短语。它不是字符串完全相等匹配，但仍属于小型关键词词典，主要问题是：

- 同义改写或自然口语不一定命中；
- 否定、反问和条件表达容易被表面词误导；
- “它”“这个项目”“第二个”等指代依赖额外上下文；
- 一个问题同时包含事实、比较和推荐时缺少稳定拆分；
- 新表达通常需要继续修改 Java 规则。

确定性规则仍适合承担安全边界、高精度快速路径和显式契约识别，但不应继续被视为完整意图理解器。

### 3.3 工具实现与生产主链路之间存在接入缺口

仓库当前定义七种只读工具：

| 工具 | 预期用途 |
|---|---|
| `GET_PROJECT` | 读取项目公开信息 |
| `GET_CASE` | 读取案例公开信息 |
| `GET_CLAIMS` | 读取主体下公开 Claim |
| `GET_EVIDENCE_FOR_CLAIMS` | 按 Claim 读取已批准 Evidence |
| `GET_TIMELINE` | 读取公开时间线 |
| `SEARCH_PUBLIC_CONTENT` | 搜索公开内容 |
| `COMPARE_PROJECTS` | 比较多个公开项目 |

`LocalPublicKnowledgeTools` 提供这些工具的 Adapter；`ConversationToolService` 还包含受限轮次、调用数量和模型 ToolPlan 校验代码。但当前 `/api/v2/answers` 的主要实际控制流是：

```text
作品集问题
→ PortfolioIntelligence
→ PortfolioRetriever
→ PortfolioIntelligenceAnswerAssembler

通用问题
→ GENERAL_KNOWLEDGE
→ toolService.enrich()
→ 因不属于 PORTFOLIO_GROUNDED/HYBRID 而原样返回
→ 通用模型
```

因此当前准确表述是：工具 Adapter 和部分规划能力已经存在，但生产主链路没有形成“选择工具—执行工具—观察结果—生成回答”的完整闭环。

### 3.4 类型存在不等于能力完整实现

代码中存在 `MODEL_GROUNDED`、`HYBRID`、`MIXED` 等枚举或结果表达，但不能据此推导它们已经形成完整生产能力。目前需要分别核实：

- 是否有真实可达的入口；
- 是否有独立规划决策；
- 是否实际执行对应工具或模型；
- 是否校验模型输出与证据一致；
- 是否有错误降级和端到端验收；
- 是否默认启用以及运行状态能否观察。

### 3.5 能力状态缺少统一词典

“有这个工具”“允许调用”“实际调用”目前容易混为一谈。后续统一采用以下状态：

| 状态 | 含义 |
|---|---|
| `REGISTERED` | 能力已在运行时目录中登记 |
| `ENABLED` | 配置和依赖允许该能力运行 |
| `ALLOWED` | 当前问题和安全策略允许选择该能力 |
| `SELECTED` | 本轮规划明确选择该能力 |
| `EXECUTED` | 已向具体 Adapter 发起执行 |
| `SUCCEEDED` | 返回合法、可消费结果 |
| `EMPTY` | 正常执行但没有匹配结果 |
| `REJECTED` | 参数、策略或安全校验拒绝执行 |
| `FAILED` | 执行异常、超时或依赖不可用 |
| `FALLBACK` | 主能力失败后使用受控降级路径 |

这些状态用于内部诊断和评测，不要求全部直接展示给访客。

## 4. 目标业务流程

本路线图的长期目标不是默认调用全部工具，而是形成一个有界、可解释、可验证的对话执行流：

```mermaid
flowchart LR
    A["访客问题与页面内存上下文"] --> B["TurnRouter"]
    B --> C["确定性边界与主体校验"]
    C --> D["PortfolioExecutionPlanner"]
    D --> E["Retriever / 只读工具"]
    E --> F["EvidenceBundle"]
    F --> G["AnswerPlan"]
    G --> H{"表达模式"}
    H -->|"确定性"| I["Deterministic Composer"]
    H -->|"可选模型"| J["Model-grounded Composer"]
    J --> K["GroundingValidator"]
    K -->|"通过"| L["结构化最终回答"]
    K -->|"失败"| I
    I --> L
```

关键原则：

1. 意图理解位于工具选择之前，不把意图分类伪装成业务工具；
2. 工具按问题需要选择，不默认全部调用；
3. 模型只接收经过筛选和验证的公开证据，不接收全量原始材料；
4. 模型主要负责表达，不拥有扩大事实范围的权力；
5. 无论是否启用模型，都能生成完整、连贯、可引用的确定性回答；
6. 每个深模块通过小接口隐藏内部复杂度，调用方和测试跨越同一个 seam。

## 6. 实施顺序与依赖

```text
阶段 0：基线与评测
    ↓ 为每次改造提供可比较证据
阶段 1：AnswerPlan + 确定性 Composer + 前端章节渲染
    ↓ 先解决用户直接可见的回答质量
阶段 2：TurnRouter
    ↓ 产出稳定任务、主体、范围和置信度
阶段 3：PortfolioExecutionPlanner + 只读工具
    ↓ 产出经过验证的 EvidenceBundle
阶段 4：MODEL_GROUNDED + GroundingValidator
    ↓ 在确定性 fallback 已可靠时增强表达
阶段 5：HYBRID + 多轮上下文 + 配置与检索矩阵
    ↓ 扩展复杂对话能力
阶段 6：真实环境验收 + 可观测性 + 清理
```

顺序不能随意倒置：

- 没有阶段 0，无法证明回答变好还是只是措辞变化；
- 没有阶段 1，更多工具只会提供更多未经组织的材料；
- 没有阶段 2，工具规划会继续依赖不稳定关键词；
- 没有阶段 3，`MODEL_GROUNDED` 缺少稳定的证据输入契约；
- 没有阶段 1 的确定性 fallback，模型失败会直接伤害可用性；
- 阶段 6 的生产容量与发布声明不能由单元测试替代。

## 8. 状态管理规则

每个任务只能使用以下项目状态：

- `待设计`：问题和目标已进入路线图，但实现接口尚未批准；
- `设计中`：正在讨论独立 Spec；
- `已批准`：Spec 已通过用户审阅；
- `实施中`：已有实施计划并正在修改代码；
- `已实现`：代码与自动测试完成，但尚未完成全部环境验收；
- `已验证`：对应验收和发布门禁通过；
- `已阻塞`：依赖明确的外部授权、环境或产品决策；
- `不采纳`：经讨论决定保留现状，并记录理由。

禁止把“存在枚举”“存在类”“测试中可构造”直接标为“已实现”；必须有真实可达控制流。禁止把“本地验证”写成“生产部署”或“线上验收”。

## 9. 总体验收标准

全部路线图完成时，系统应满足：

1. 事实型作品集问题返回按语义组织的连贯回答，而不是检索段落清单；
2. 每个关键事实仍能追溯到公开 Claim 和 APPROVED Evidence；
3. 路由能够处理常见改写、否定、指代、比较和推荐表达；
4. 低置信度或主体冲突时主动澄清，不静默猜测；
5. 工具只在需要时被选择，并能解释其生命周期和失败原因；
6. `MODEL_GROUNDED` 真正可达，输出必须通过证据校验；
7. 模型关闭或失败时，确定性回答仍完整、连贯、可用；
8. `HYBRID/MIXED` 的公开事实与通用解释来源清晰分区；
9. 全链路不记录访客原文，不扩大公开数据范围；
10. 离线评测、真实 Provider 验收、数据库/本地模型验收和前端 E2E 各自有明确 Verdict；
11. 文档能准确区分当前实现、已批准设计、实施状态和生产状态。

## 10. 当前决议

1. 采用“总路线图 + 分阶段 Spec + 批准后实施 Plan”的文档结构；
2. 第一份独立设计聚焦阶段 1：回答结构化与前端呈现；
3. 模型在第一阶段不是必需依赖，确定性 Composer 必须先成为可靠 fallback；
4. 语义路由、工具编排和模型证据表达分别设计，不合并为一个超大实施包；
5. 当前不默认启用或调用全部工具；目标是按场景选择最小必要能力；
6. 当前不把意图分类实现为业务工具；它属于 `TurnRouter` 的内部决策能力。
