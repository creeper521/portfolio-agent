# Agent 项目演进日志

> 本文按日期和开发阶段记录 Agent 项目功能、重要修复、产品决策与技术选型的演进。
> 本文不记录具体代码步骤、测试过程或 Git 提交信息；当前能力边界仍以《当前实现状态》和《文档状态索引》为准。

## 状态说明

- **提出**：形成想法或待确认方向。
- **选定**：完成方案选择，但尚未实现。
- **已实现**：能力已经进入当前项目。
- **受限启用**：已经实现，但受审批、配置或环境限制。
- **默认关闭**：已经实现，但默认运行路径不启用。
- **已取代**：曾经采用，后来被新方案替换。
- **未部署**：本地能力已经完成，尚未进入生产环境。

## 2026-07-14

### 阶段一：确定公开实习作品集 Agent 的产品边界

- 项目被定义为面向公开访问者的实习作品集 Agent，而不是连接私人知识库的个人 Copilot。
- 运行时数据源限定为经过审核、脱敏和批准的公开快照；私人 Obsidian、原始日报、凭据和未经审核的截图不进入公开运行时。
- 首个纵向切片收敛为一个公开项目、一个可执行问题和一组公开证据，以确定性回答建立最小闭环。
- 回答结构围绕背景、职责、方案、验证和状态组织，避免把计划、协作或学习记录夸大为独立交付成果。
- 当前状态：**已实现**，并成为后续所有能力扩展的事实与隐私底线。
- 相关设计：[实习作品集 V0 设计](superpowers/specs/2026-07-14-internship-portfolio-v0-design.md)

### 阶段二：提出第一版代码架构整理方向

- 针对早期后端中接口、应用、领域和基础设施边界混杂的问题，提出按职责重新组织代码的方案。
- 这一版方案建立了“公开作品集事实”和“回答能力”需要隔离的基本方向。
- 后续项目选择了更明确的模块化单体包结构，因此本阶段的具体重构计划不再作为当前实施依据。
- 当前状态：**已取代**。
- 相关设计：[早期代码架构重构设计](superpowers/specs/2026-07-14-codebase-architecture-refactor-design.md)

## 2026-07-16

### 阶段一：建立模块化单体后端

- 后端确立 `common / portfolio / answer` 三个顶层模块，在一个 Spring Boot 进程和一个交付制品内保持清晰边界。
- `portfolio` 负责公开事实、校验和查询；`answer` 负责问题理解与回答编排；跨模块读取通过专用 Gateway 完成。
- Answer 拥有自己的结果和证据表达，不再把 Portfolio 的领域对象直接泄漏到回答接口。
- 旧的通用分层包结构被移除，模块依赖方向成为项目长期架构基线。
- 当前状态：**已实现**。
- 相关设计：[模块化单体包设计](superpowers/specs/2026-07-16-modular-monolith-package-design.md)

### 阶段二：重建公开作品集前端

- 前端从早期设计原型演进为 Vue 3、TypeScript 和 Vite 的正式单页应用。
- 建立首页、项目目录、项目详情、时间线、证据中心和 Agent 工作台等主要页面骨架。
- 首页形成工程档案 Hero、可信度摘要、角色化提问和深入探索四层信息结构。
- Agent 工作台确立会话、对话和证据三栏结构，并坚持访客会话只存在当前页面内存。
- 当前状态：**已实现**；后续视觉、Case 信息架构和工作台交互继续演进。
- 相关设计：[作品集前端完整重建设计](superpowers/specs/2026-07-16-portfolio-frontend-full-rebuild-design.md)

### 阶段三：对齐前端原型的视觉与交互基线

- 正式前端开始吸收纸面卷宗原型的暖纸、暖黑、暗红和细线排版语言。
- 页面响应式、焦点、减少动态效果和工作台布局被纳入正式前端要求。
- 这一阶段建立的视觉方向有效，但具体工作台外壳、断点和交互细节后来由 7 月 22–24 日设计进一步取代。
- 当前状态：**部分被后续设计取代**。
- 相关设计：[前端原型保真对齐设计](superpowers/specs/2026-07-16-portfolio-prototype-fidelity-alignment-design.md)

### 阶段四：澄清查询结果与校验职责

- 查询服务返回自己的结果模型，公开响应 DTO 只在 Web 边界生成。
- 快照校验失败与单次查询失败被区分，避免局部错误污染整个公开内容读取流程。
- 当前状态：**已实现**。
- 相关计划：[结果与校验边界重构计划](superpowers/plans/2026-07-16-portfolio-result-validation-boundary-refactor.md)

- 首页轻量提问和完整 Agent 工作台开始使用后端回答接口，而不是只依赖前端固定演示文案。
- 对话请求增加过期结果保护，切换页面或问题后返回的旧结果不会覆盖当前状态。
- 前端与后端被整合为单一可打包制品，为后续运行时可信和发布门禁提供交付基线。

## 2026-07-20

### 阶段一：确定运行时可信模型

- 回答契约从简单文本扩展为能够明确表达回答结果、生成方式、来源和核验状态的四维模型。
- 同一次回答只读取一个不可变公开快照，避免项目、证据和推荐问题来自不同内容版本。
- 访客问题和会话坚持不落库、不写日志、不进入 URL 或浏览器持久化存储。
- 未知问题、越界主体和能力不足场景采用明确的边界响应，不用猜测或无依据生成填补空白。
- 当前状态：**已实现**。
- 相关设计：[运行时可信设计](superpowers/specs/2026-07-20-portfolio-agent-runtime-trust-design.md)

## 2026-07-21

### 阶段一：建立 Claim、Evidence 与内容治理体系

- 公开内容从单一项目 JSON 演进为 Project、Claim、Evidence、Claim–Evidence 关联、TimelineEvent 和 QuestionPreset 等明确实体。
- Claim 只表达允许公开的事实陈述，Evidence 负责支持强度和公开状态，两者不再混为同一个对象。
- 候选准备、审核、人工批准、发布和回滚被拆成独立步骤，任何自动流程都不能替代内容所有者批准。
- 受控学习只允许产生待审核候选，不能直接改变公开运行时。
- 当前状态：**已实现**。
- 相关设计：[内容治理设计](superpowers/specs/2026-07-21-portfolio-agent-content-governance-design.md)

### 阶段二：把未来智能能力拆为 C1、C2 和 C3

- C1 定义为在固定公开事实基础上的可选模型表达，不允许模型改变事实范围。
- C2 定义为本地公开检索、固定只读工具和稳定引用式多轮，重点解决公开内容扩展后的可检索性和追问能力。
- C3 定义为更通用的 Provider、工具、Hook、编排和任务抽象，但必须逐项准入，不能因为形成总设计就视为全部可用。
- 当前状态：C1、C2 已进入后续实现；C3 只有 Model Provider Registry 获准并实现，其余能力仍未准入。
- 相关设计：[未来智能能力设计](superpowers/specs/2026-07-21-portfolio-agent-future-intelligence-design.md)

## 2026-07-22

### 阶段一：落地运行时可信与内容治理

- 四维回答契约、不可变快照、严格公开主体边界和页面内存会话进入正式运行时。
- 内容治理具备候选准备、审核、批准、发布和回滚所需的封闭流程。
- 发布包被区分为人工批准的规范公开载荷和服务器生成的运行制品，运行时只读取当前激活版本。
- 当前状态：**已实现**。
- 相关设计：[运行时可信设计](superpowers/specs/2026-07-20-portfolio-agent-runtime-trust-design.md)、[内容治理设计](superpowers/specs/2026-07-21-portfolio-agent-content-governance-design.md)

### 阶段二：实现 C1 受限模型表达

- 服务端先生成白名单 AnswerPlan，再允许单个选定 Provider 对公开事实进行语言表达。
- 模型草稿必须通过结构、长度、事实引用和公开范围检查；不合格结果回退到同一 AnswerPlan 的确定性表达。
- Provider 通过部署配置显式选择，不保存供应商会话标识，也不自动切换到其他 Provider。
- 当前状态：**受限启用、默认关闭**；需要模型开关、密钥和独立数据策略批准。
- 相关设计：[未来智能能力设计](superpowers/specs/2026-07-21-portfolio-agent-future-intelligence-design.md)

### 阶段三：实现 C2a 本地公开检索

- 技术选型确定为本地 BGE-small-zh-v1.5 INT8 ONNX，不向外部 Embedding 服务发送公开文档或访客查询。
- 检索路线由关键词、向量、RRF 融合和 Grounding Gate 组成；只有证据充分时才返回检索型回答。
- RAG 文档、关键词索引和向量索引与 ContentBundle 原子绑定，不能独立激活或回滚。
- 当前状态：**已实现、默认关闭**；运行时需要完整七文件 Bundle 和本地固定模型。
- 相关设计：[C2a 本地公开检索设计](superpowers/specs/2026-07-22-portfolio-agent-c2a-local-public-retrieval-design.md)

### 阶段四：实现 C2b 固定只读工具与引用式多轮

- 工具能力限定为查询项目、Claim、Evidence、时间线、公开搜索和项目比较六类固定读操作。
- 服务端根据封闭意图生成 ToolPlan，工具不能访问文件系统、网络、私有治理目录或写接口。
- 多轮上下文只保留公开内容版本和稳定实体引用，不保存历史问题、回答正文或 Provider thread。
- 内容版本变化或引用失效时重新核对并明确返回边界，而不是沿用过期事实。
- 当前状态：**已实现**。
- 相关设计：[未来智能能力设计](superpowers/specs/2026-07-21-portfolio-agent-future-intelligence-design.md)

### 阶段五：C3 只准入内建 Model Provider Registry

- Provider 选择从分散配置收敛到不可变 Registry 快照。
- Registry 只内建 DeepSeek V4 Flash 与 GLM-4.7，每次部署仍显式选择一个 Provider。
- 不提供自动故障转移、跨 Provider 重发或动态发现。
- Tool Registry、Hook、Orchestrator、多 Agent、DurableTask 和持久会话没有因此获得准入。
- 当前状态：Registry **已实现**；其余 C3 能力**未实现**。
- 相关设计：[C3 Model Provider Registry 设计](superpowers/specs/2026-07-22-portfolio-agent-c3-model-provider-registry-design.md)

### 阶段六：Agent 工作台转向浅色纸阶

- 三栏工作台从偏深色的实验界面调整为更清晰的浅色纸张层级。
- 深色实心控件被收敛到“新对话”和“发送”等关键动作，降低大面积深色带来的压迫感。
- 这套方案成为后续暖黑舞台和米色悬浮工作台的视觉前序。
- 当前状态：**已实现后被后续暖调作品窗口取代**。
- 相关设计：[浅色 Agent 工作台设计](superpowers/specs/2026-07-22-portfolio-agent-light-workspace-palette-design.md)

### 阶段七：确定求职作品集的内容补全路线

- 内容建设从“继续堆功能”调整为围绕长主线、具体功能、故障案例、评测和知识产出分层。
- 明确页面视觉与 Agent 能力需要按项目纵向切片共同交付，再做全站整合、质量收口和部署。

### 阶段二：建立真实本地检索对比体系

- 检索评估从少量人工观察演进为 Keyword、Vector 和 Hybrid 三条路线的统一基准。
